# 全链路测试前置：各角色必须做到什么

> 日期：2026-10-31  
> 配套：`docs/全链路_下单到分账到提现到账_20261031.md`  
> 口径来源：`docs/API接口文档_v8.25` §60（业主小店/一级代理）、§92（收款账户）、§97（进件）、§99（楼长）、§8（订单支付）

---

## 0. 一条原则：链路是串行的，上游不做完下游必然卡死

```
平台配物业分成 → 物业开开关/任命楼长 → 商家挂接+进件 → 住户才能下单支付 → 确认收货才分账 → 绑定收款才能提现
```

所以测试不是"每个角色把自己功能点一遍"，而是**按依赖顺序把上游一次性铺好**。下面按角色列，每个角色只写三类信息：必须完成什么、入口在哪、缺了会怎样（报什么错）。

---

## 1. 平台管理员（全局配置 + 唯一能改费率的人）

| # | 必须完成                                                   | 入口                                                 | 缺了会怎样                                 |
| - | ------------------------------------------------------ | -------------------------------------------------- | ------------------------------------- |
| 1 | 物业公司存在且**分成三档合计 = 100%**                               | 参数配置 → 分账（`PATCH /property-companies/{id}/config`） | 保存直接报 `97006`，分账比例算不出来                |
| 2 | 打开目标小区的**积分 / 物业币开关**                                  | 同上                                                 | 住户端积分/物业币入口不可用，支付方式选不了                |
| 3 | 确认**配送费抽成**（默认 10%）                                    | **平台分成配置**（`PUT /admin/platform-share-rates`）      | 配送员收入按 0 或按旧值算，对账差                    |
| 4 | 商家 `commissionRate` 就位                                 | 商家挂接配置 / 入驻审核通过时写入 / 价格审批                          | 下单返回 `60006`（未挂接），链路从第一步就断            |
| 5 | 审核商家入驻、组长/技工申请                                         | 商家入驻审核                                             | 商家不存在或 `status` 非 active，无法下单         |
| 6 | 审核提现（`approved` → 打款后 `completed` + 凭证）                | 商家提现审核 / 角色提现审核 / 物业币提现审核                          | 钱停在 `pending`，永远不到账                   |
| 7 | 开通一级代理（`is_distributor=1`）                             | 后台                                                 | 业主小店拿不到货，件数制链路测不了                     |
| 8 | 确认**测试环境 B 方案开关** `courierShareFromDeliveryFee = true` | 环境配置（非页面）                                          | 仍是 A 方案：配送员被保底 0.6~5，小平台盘会出现倒贴，例数全对不上 |

> 平台是唯一能改 5 个分成率 + 提现手续费率的角色。物业领导传这些字段必得 `403 / 20004`——**这是预期，不是 bug**，测试时不要当失败报。

## 2. 物业领导（本物业运营参数 + 楼长）

| # | 必须完成                          | 入口                                                | 缺了会怎样                             |
| - | ----------------------------- | ------------------------------------------------- | --------------------------------- |
| 1 | 本物业积分/物业币开关、物业币有效期            | 参数配置（本物业）                                         | 同平台第 2 条                          |
| 2 | 商城抵扣 3 项（能否用物业币抵扣、比例、起抵金额）    | 参数配置 → 物业币（`PUT /admin/property-coin/mall-rules`） | 混合支付里物业币抵扣额为 0，测不出抵扣              |
| 3 | 物业币展示开关                       | 参数配置（需 `coin:display_control`）                    | 住户端看不到物业币入口。**若开关不显示，是预设缺码，不是缺陷** |
| 4 | **任命楼长**：小区 + 单元 + 费率（默认 10%） | 楼长管理（`POST /admin/building-leaders`）              | `buildingLeaderShare` 恒为 0，物业份不切分 |
| 5 | 确认楼长与住户同属**同一小区同一单元**         | 楼长管理                                              | 下单时解析不到楼长，快照为空 → 不产生楼长分成          |
| 6 | 审核本物业的角色提现 / 物业币提现            | 提现审核                                              | 同平台第 6 条                          |

**楼长的特殊性**：它是「住户 + 楼长」复合身份，`residents.role` 仍是 `resident`，靠 `building_leaders.status='active'` 识别。测试时**不要新建一个 role=building_leader 的账号**，那会走历史兜底逻辑。

## 3. 商家（货源 + 收款能力）

| # | 必须完成                                                   | 入口                         | 缺了会怎样                                   |
| - | ------------------------------------------------------ | -------------------------- | --------------------------------------- |
| 1 | 入驻审核通过、`status=active`                                 | 管理端审核                      | 下单 `60001` 商家不存在                        |
| 2 | **在该物业下有挂接配置**（含 `commissionRate`、`pointExchangeRate`） | 审核通过自动建 / 后台补              | 下单与支付均返回 `60006`。这是最常见的卡点               |
| 3 | 上架商品、有库存、设配送费                                          | 商家端商品管理                    | 下不了单                                    |
| 4 | **微信进件到 `finished`**（拿到 `subMchid`）                    | 商家端「微信收款」→ 人脸核验 → 签约       | 不能用微信支付，返回 `99004` / `99003`，只能回退积分/物业币 |
| 5 | 收款账户就位（`ownerType=merchant`）                           | `POST /admin/cbk/accounts` | 提现审核通过了也打不出款                            |

**进件状态机**（要盯着看，非终态会一直卡）：*

```
init → submitted → auditing → legal_validating / signing → finished
                                                      └→ rejected（可改资料重提）
```

`legal_validating` / `signing` 会返回有时效的链接，**必须点完人脸核验和签约**，否则永远到不了 `finished`。

## 4. 配送员

| # | 必须完成                        | 入口                         | 缺了会怎样                         |
| - | --------------------------- | -------------------------- | ----------------------------- |
| 1 | 账号存在且可抢单                    | 角色账号管理                     | 无配送单可抢                        |
| 2 | **微信侧授权收款**（openid 预授权）     | 微信内授权                      | 配送费分账直发 openid 会失败，账上有钱但到不了微信 |
| 3 | 绑定收款账户（`ownerType=courier`） | `POST /admin/cbk/accounts` | 提现打不出款                        |

**测试要点**：配送员收入与订单结算**无关**。点「送达」（`POST /deliveries/{id}/complete`）那一刻就入账，订单还停在 `delivering`。验收时别等订单完成才看配送员钱包。

---

## 5. 统筹 / 板块负责人 / 个体负责人（四层分成树）

| # | 必须完成                                                                    | 入口                                     | 缺了会怎样           |
| - | ----------------------------------------------------------------------- | -------------------------------------- | --------------- |
| 1 | 身份记录 `status=active` 且挂在**该物业**下                                        | 负责人管理                                  | 分账时找不到人，该层份为空   |
| 2 | 绑定收款方式（`ownerType=coordinator` / `sector_leader` / `individual_leader`） | 本人「我的收款方式」或 `POST /admin/cbk/accounts` | **记账上有钱，但打不出去** |

这三个角色**不走微信分账**，是平台佣金到账后由「微信商家转账」出款。所以「钱包有余额」和「钱到微信」之间还差一个绑定动作。

## 6. 住户（买家）

| # | 必须完成                     | 入口                                             | 缺了会怎样                  |
| - | ------------------------ | ---------------------------------------------- | ---------------------- |
| 1 | 绑定小区 + 房号/地址             | 小程序个人中心                                        | 下单地址校验失败               |
| 2 | 绑定 openid                | 微信登录                                           | 微信支付无 `openid`，`99001` |
| 3 | 积分余额（测积分支付）、物业币余额（测混合支付） | 物业发放 / 缴费返积分 / `POST /property-coins/recharge` | 余额不足 `40001` / `50001` |
| 4 | 家庭（可选，测家庭余额支付）           | 家庭管理                                           | —                      |

⚠️ **悖论提醒**：物业币充值接口在 `coinEnabled=false` 时会被拒绝。所以要测「关掉物业币后支付被拒」，必须**先开着充好余额，再关开关**，顺序反了会卡在充值这一步。

---

## 7. 住户（卖家 · 业主小店）

| # | 必须完成                              | 入口                                       | 缺了会怎样               |
| - | --------------------------------- | ---------------------------------------- | ------------------- |
| 1 | 申请业主商户 → 审核通过 `active`            | 管理端审核                                    | 无店铺主体，下单 `60036`    |
| 2 | 缴保证金（默认 500，平台可配）                 | 小程序 → 保证金支付                              | 不能上架                |
| 3 | **从一级代理拿货**（`quantity` 件，扣一级代理库存） | 选品上架 `POST /resident-merchants/listings` | 无可售件数               |
| 4 | 设零售价 **≥ 进货价**                    | 同上                                       | `10002`「零售价不能低于进货价」 |
| 5 | 收款方式绑定                            | —                                        | 卖货钱包有钱提不出来          |

**不要期待它进四层分账**：`listingId != null` 的订单在结算时**跳过**物业四级分成/楼长分成，只走件数制（货款给一级代理、佣金给平台、差价给店主）。测这条链路时如果去查 `distribution_records` 找不到四层数据，是正常的。

件数守恒要盯住：`拿货件数 = 已卖 + 支付锁定中 + 可售`。测试退款后要确认可售件数回补、卖完下架的能自动重新上架。

## 8. 一级代理（业主小店的货源方）

| # | 必须完成                                                                | 入口        | 缺了会怎样                 |
| - | ------------------------------------------------------------------- | --------- | --------------------- |
| 1 | 开通 `is_distributor=1`                                               | 后台        | 不能设货源                 |
| 2 | 建货源商品：`wholesalePrice` / `suggestedRetailPrice` / `stock`（库存**件数**） | 一级代理端货源管理 | 业主小店无货可选，`60033` 库存不足 |

## 9. 按阶段的最短可测路径

只测「下单 → 分账」，最少需要这些就位；每多测一段，右边一列就必须补上。

| 阶段         | 最少就绪                            | 缺了卡在哪                                 |
| ---------- | ------------------------------- | ------------------------------------- |
| 下单         | 商家 active + 挂接配置 + 商品有货 + 住户绑房号 | `60006` / `60001`                     |
| 支付（积分/物业币） | 对应开关打开 + 住户有余额                  | `97070` / `97071` / `40001` / `50001` |
| 支付（微信）     | 商家进件 `finished` + 住户 openid     | `99004` / `99001`                     |
| 配送         | 配送员账号 + 订单进入配送池                 | 无单可抢                                  |
| 分账落地       | 确认收货（或等自动确认）                    | 订单停在 `delivering`，分成不生成               |
| 楼长分成       | 楼长 active + 与买家同小区同单元           | `buildingLeaderShare=0`               |
| 提现申请       | 钱包可提现 > 0                       | `94003`                               |
| 提现到账       | 平台审核 + 财务线下打款 + 回填凭证            | 停在 `pending` / `approved`             |

## 10. 卡点速查（按报错码反查是谁没做）

| 码                           | 含义                  | 谁没做                                                           |
| --------------------------- | ------------------- | ------------------------------------------------------------- |
| `60006`                     | 商家在该物业下未完成挂接配置      | 平台：没给商家建 `merchant_property_configs`                          |
| `60001`                     | 商家不存在               | 平台：入驻没审核通过                                                    |
| `99004` / `99003`           | 未进件 / 收付通未配置        | 商家：进件没到 `finished`；或环境没开收付通                                   |
| `97070` / `97071`           | 本小区未启用积分 / 物业币      | 物业或平台：开关没开                                                    |
| `40003` / `50006`           | 积分/物业币功能已停用（旧码口径）   | 同上报错，**但码不一样，见 §11**                                          |
| `40001` / `50001`           | 积分 / 物业币余额不足        | 住户：余额不够                                                       |
| `80025` / `80026` / `80027` | 定向余额不足 / 越权 / 未选主商家 | 住户侧：食堂定向余额传参不对                                                |
| `94003`                     | 可提现余额不足             | 钱还没结算，或在途未释放                                                  |
| `94005`                     | `withdrawalBlocked` | 该账号被风控（如欠物业费）                                                 |
| `97006`                     | 三档分成合计不为 100%       | 平台：分成比例没配平                                                    |
| `70002`                     | 订单状态不允许操作           | 用 `courier` 想直接置 `completed`（应该走 `/deliveries/{id}/complete`） |

## 11. 开测前必须确认的一件事：错误码到底是哪一套

关掉积分/物业币后，写接口的拒绝码文档里有**两套口径**：

| 口径 | 出处                 | 码                             |
| -- | ------------------ | ----------------------------- |
| 旧  | 接口文档 §5.x / §21154 | `40003`（积分停用）/ `50006`（物业币停用） |
| 新  | 后端 2026-10-30 回复   | `97070` / `97071`             |

前端两套都已在码表里（`97070/97071` 是这次新加的，`40003/50006` 是原文档口径未删）。

**所以测试第一条应该先探一下**：关掉某物业的积分开关，调一个积分写接口，看实际返回哪个码。

- 返回 `97070` → 后端已部署新码，按新口径验收；
- 返回 `40003` → 新码没生效（可能部署的是旧包），此时报「97070 不生效」是误判，要先确认部署版本。

这一步花两分钟，能避免后面一连串误判。

## 12. 建议的测试数据（便于心算核对）

| 项         | 建议值                      | 为什么                        |
| --------- | ------------------------ | -------------------------- |
| 商家佣金率     | `0.10`                   | 商品 10 元 → 平台盘正好 1.00，心算不费劲 |
| 平台盘三档     | 平台 10% / 物业 60% / 统筹 30% | 1.00 → 0.10 / 0.60 / 0.30  |
| 配送费抽成     | 10%                      | 配送 1 元 → 平台 0.10、配送员 0.90  |
| 商品价 + 配送费 | 10 + 1                   | 两线都能凑整                     |
| 楼长费率      | 10%                      | 物业 0.60 → 楼长 0.06、物业留 0.54 |
| 提现手续费率    | 6‰                       | 提 5 元 → 手续费 0.03、实到 4.97   |

配成这套数字后，第 5 节的分账表可以直接口算核对，不用开计算器。

## 13. 一页 checklist（可直接打印）

**平台**

- [ ] 物业分成三档 = 100%
- [ ] 积分/物业币开关已开
- [ ] 配送费抽成确认（默认 10%）
- [ ] 商家已挂接 + `commissionRate` 就位
- [ ] B 方案开关 `courierShareFromDeliveryFee = true`
- [ ] 提现审核人到位（能点到 `completed` 并上传凭证）

**物业**

- [ ] 本物业参数已配（开关/有效期/抵扣）
- [ ] 楼长已任命且与买家同小区同单元
- [ ] 物业币展示开关可见（预设含 `coin:display_control`）

**商家**

- [ ] 入驻 active + 挂接配置
- [ ] 商品在架有库存
- [ ] 微信进件 `finished`
- [ ] 收款账户已绑

**配送员**

- [ ] 账号可抢单
- [ ] 微信收款已授权
- [ ] 收款账户已绑

**负责人（统筹/板块/个体）**

- [ ] 身份 active 且挂在本物业
- [ ] 收款方式已绑

**住户（买家）**

- [ ] 小区 + 房号已绑定
- [ ] openid 已绑
- [ ] 积分/物业币余额充足（先充再关开关）

**住户（卖家）/ 一级代理**

- [ ] 业主商户审核 active + 保证金已缴
- [ ] 一级代理 `is_distributor=1` 且有货源库存
- [ ] 已拿货上架，零售价 ≥ 进货价

**通用**

- [ ] 已确认错误码是新码（`97070/97071`）还是旧码（`40003/50006`）
