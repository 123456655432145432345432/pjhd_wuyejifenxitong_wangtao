## 1. 资金模型（务必背下来，公式已订正）

一笔订单完成后，后端自动写一条分账记录，两层拆分：

```
用户实付 totalAmount
│
├─【第一层】商家份额 merchantShare = totalAmount × (1 − commissionRate)   → 商家可提现
│
└─【第一层】平台盘 distributableAmount = totalAmount × commissionRate − pointCost − coinCost
      │   （注意：先乘抽佣比例，再扣积分/物业币成本）
      ├─ 平台服务费 platformShare        （公司内部账，无提现入口）
      ├─ 物业       propertyShare         → 物业分成账户 settlementBalance
      ├─ 统筹       coordinatorShare      → 统筹提现
      ├─ 区块       sectorLeaderShare     → 区块提现
      ├─ 个体       individualLeaderShare → 个体提现
      └─ 快递       courierShare          → 配送员可提现（A 方案，见 §6）
```

### 必记要点
- `commissionRate` = **平台盘占比**（后端已确认），**按每个外部商家单独配置**。
  - 例：`commissionRate=0.20`、`totalAmount=100` → 商家=80，平台盘=100×0.20=20。
- **易错点（务必注意）**：平台盘是 `totalAmount × commissionRate` **再扣** `pointCost/coinCost`，**不是**「订单额 − 成本」。
  - 交付文档「100 → 平台盘 20」示例**没算积分成本**，真实 `distributableAmount` 会更小。
  - 全额积分/物业币支付的订单，平台盘可能被扣到 **0**，现金分成为空 —— **这是预期，不是 bug**。
- 后端 `DistributionConverter` 已实时算好所有 `*Share`，字段**恒有值**，移动端**只读不算**。

GET /distribution/records

### 单条字段 `DistributionRecordItem`
| 字段 | 类型 | 含义 |
|------|------|------|
| `id` | string | 记录 ID |
| `orderId` / `orderNo` | string | 订单 ID / 编号 |
| `merchantId` / `merchantName` | string | 商家 |

| `pointCost` / `coinCost` | number | 积分 / 物业币成本（从平台盘扣） |
| `distributableAmount` | number | 平台盘（后端算好，直接用） |
| `merchantShare` | number | 商家份额（**恒有值**） |
| `platformShare` | number | 平台服务费 |
| `propertyShare` | number | 物业份额 |
| `courierShare` | number | 快递份额（A 方案，见 §6） |
| `coordinatorShare` | number | 统筹份额 |
| `sectorLeaderShare` | number | 区块份额 |
| `individualLeaderShare` | number | 个体份额 |
| `coordinatorId/Name`、`sectorLeaderId/Name`、`individualLeaderId/Name` | string | 各负责人 |
| `status` | string | 记录状态 |
| `createdAt` | string | 创建时间（ISO） |

### 字段读取规则（照抄管理端 `src/utils/distribution.ts`）
1. 每个份额优先读 `*Share` → 回退 `*Amount` → 回退 snake_case（如 `merchant_share`）。
2. `merchantShare` **后端恒返回**，下面兜底**仅作防御、正常不触发、不要依赖**：
   - 有 `totalAmount`+`commissionRate` → `totalAmount ×(1 − commissionRate)`
   - 否则 `distributableAmount < totalAmount` → `totalAmount − distributableAmount`
3. **按角色只显自己那一列**：商家视角只显 `merchantShare`；管理/统筹可全显。

## 4. 下单 / 结算试算（商家侧「本单预计可得」）

### 接口
```
GET /distribution/calculate?merchantId=&totalAmount=100&pointUsed=&coinUsed=&propertyCompanyId=
```
### 返回 `DistributionCalculateResult`
无 id，字段同明细，另含 v4.10：`commissionBaseAmount`（抽佣基础额 = 订单额 × 抽佣率，尚未扣积分/币成本）。

关系：`commissionBaseAmount − pointCost − coinCost = distributableAmount`（实际可分配平台盘）。

其余字段：`totalAmount, commissionRate, pointCost, coinCost, distributableAmount, merchantShare, platformShare, propertyShare, courierShare, coordinatorShare, sectorLeaderShare, individualLeaderShare`。

- 用途：结算页给商家**预览**，避免自己猜。
- 文案：**「预计可得」，非「已到账」**；勿把示例「用户付 100 → 平台盘 20」直接当作可分配额（那是抽佣基础额）。

## 5. 商家抽佣 commissionRate（第一层，按店配置）

- **语义（后端确认）**：= 平台盘占比，直接作乘数 `distributableAmount = totalAmount × commissionRate − 积分/币成本`。
  - `0.10` = 商家直分 90%、平台盘 10%。
- 变更走价格审批：`itemType = merchant_distribution`，**审批通过后才生效**，当前值不会立即变。
- 移动端商家端展示抽佣时，标注「审批通过后生效」。

## 6. 配送员收入（A 方案 · 必须严格遵守）

**结论**：配送员到手 = `courierEarning`，且**与分账记录 `courierShare` 是同一笔、数值一致**。

### 计算口径（后端算，移动端只展示）· **B 方案（现网）**
```
platformDeliveryShare = deliveryFee × platformDeliveryShareRate   // 默认 10%
courierEarning        = deliveryFee − platformDeliveryShare       // 无保底
```
- **禁止**再用「平台盘 × 15% / ¥0.6~¥5 保底」（已废止的 A 方案）。
- 管理端常量见 `src/constants/courierEarning.ts`（仅配送费抽成，无 15%）。

### 展示要求
- 抢单/任务列表「预计收入」= `courierEarning`（缺省勿用平台盘×15% 本地算）。
- 分账明细列文案用「**配送员收入**」，与提现同源（来自配送费）。
- **禁止**再显示/依赖「按单固定 0.35 元」「平台盘×15%」等旧逻辑。

### 入账触发
```
POST /deliveries/{id}/complete  成功
  → 立刻 GET /courier-managers/my 刷新可提现（不要本地累加）
```

## 7. 各角色提现（⚠ 端点存在性需逐一确认）

### 统一规则
- 提现金额 ≤ 可提现余额（后端校验，前端只做体验兜底、勿本地累加）。
- 手续费 `feeRate = 0.006`（6‰）；`actualAmount = amount − feeAmount`。
- 状态机：`pending → approved → completed`（或 `rejected`）。
- 请求体：`{ "amount": number }`（个别角色可能带 `bankCardId`，以各 DTO 为准）。

### 返回 `RoleWithdrawalItem`
```
id, amount, feeRate, feeAmount, actualAmount, status,
withdrawalType, applicantId, residentId, propertyCompanyId,
auditedAt, createdAt, completedAt, remark
```

### 端点表（v4.10 已确认齐全，可对接）
| 角色 | 申请 | 记录 | 可提现来源 | 确认状态 |
|------|------|------|-----------|---------|
| 物业(分成) | `POST /admin/property-companies/{id}/settlement-withdrawals` | 同名 GET | `settlement-balance` | ✅ 已确认 |
| 商家 | `POST /merchant/withdrawals` | `GET /merchant/withdrawals` | `GET /merchants/my → withdrawableAmount` | ✅ 已确认 |
| 配送员 | `POST /courier-managers/my/withdrawals` | `GET /courier-managers/my/withdrawals` | `GET /courier-managers/my` | ✅ 已确认 |
| 统筹 | `POST /coordinators/{id}/withdrawals` | `GET /coordinators/{id}/withdrawals` | `GET /coordinators/my → id` | ✅ 已确认 |
| 区块 | `POST /sector-leaders/{id}/withdrawals` | `GET /sector-leaders/{id}/withdrawals` | `GET /sector-leaders/my → id` | ✅ 已确认 |

## 9. 文案与状态红线

1. 所有分账金额标「待结算 / 可提现」，**禁止**「已分账到账 / 付款即到账」。
2. 全额积分订单现金分成为空 / 平台盘为 0 —— **预期，不是 bug**。
3. 平台服务费为 0 → 后端确认为**历史脏数据**（新单有 0.10 兜底不会为 0）。移动端**照实展示**，可提示「历史数据」，**不要报错**。
4. 状态由后端 `status` 驱动；金额一律以 `*Share / amount / settlementBalance / withdrawableAmount` 为准，前端不算。

## 10. 错误码（提现相关）
| 码 | 含义 | 移动端处理 |
|----|------|-----------|
| `94003` | 提现金额超过可提现余额 | 提示超额，禁止提交 |
| `94005` | 账户被冻结 / 不可提现（`withdrawalBlocked=true`） | 金额置 0 且置灰，提示「请及时缴纳物业费或联系管理人员」 |

> 冻结提示语固定为上句，**不写「物业公司冻结」**，不把责任推给物业。

## 11. 联调验收清单（逐条打勾）

### 分账明细
- [ ] 完成一笔现金订单 → 明细出现该记录。
- [ ] `merchantShare ≈ totalAmount × (1 − commissionRate)`（后端恒返回，非前端算）。
- [ ] 全额积分订单 → 平台盘/现金分成可为 0，页面正常无报错。
- [ ] 平台服务费为 0 的历史单 → 展示 0 并标「历史数据」，不报错。
- [ ] 分页在 `list` 和 `content` 两种返回下都能翻页。

### 配送员（A 方案合轨）
同一笔已完成订单，三处数值应相等：
- [ ] 分账明细「快递收入」= X
- [ ] 配送任务「预计收入」= X
- [ ] 完成配送后可提现增量 ≈ X
- [ ] 平台盘小 → X 抬到 0.60；平台盘大 → X 封顶 5.00。
- [ ] 若出现「明细算 3、提现只加 0.35」→ 后端未合轨，**报后端**。

### 提现
- [ ] 申请金额 ≤ 可提现；超额触发 `94003`。
- [ ] `withdrawalBlocked=true` → 金额 0、置灰、`94005` 提示语正确。
- [ ] 申请成功回显 `feeAmount` / `actualAmount`（6‰）。
- [ ] 非物业角色提现端点已与后端确认存在再接。

### 统计
- [ ] 统计页展示「总订单额 / 商家实得」（读 `summary.totalOrderAmount` / `summary.merchantAmount`）。
- [ ] 试算页展示 `commissionBaseAmount`，并与 `distributableAmount` 关系正确。

## 附 B：B 方案常量（照抄管理端 `src/constants/courierEarning.ts`）

```typescript
/** 平台从配送费抽取比例默认值 */
export const DEFAULT_PLATFORM_DELIVERY_SHARE_RATE = 0.1

/** 配送员收入 = 配送费 − 平台抽成（无保底）；有 courierEarning/courierShare 时优先用后端值 */
export function calcCourierEarningFromDeliveryFee(
  deliveryFee?: number | null,
  platformDeliveryShareRate = DEFAULT_PLATFORM_DELIVERY_SHARE_RATE
) {
  if (deliveryFee == null || Number.isNaN(Number(deliveryFee))) return undefined
  const fee = Number(deliveryFee)
  if (!Number.isFinite(fee) || fee < 0) return undefined
  const rate = Math.min(Math.max(Number(platformDeliveryShareRate) || 0, 0), 1)
  const platformCut = Math.round(fee * rate * 100) / 100
  return Math.round(Math.max(fee - platformCut, 0) * 100) / 100
}
```

## 附 C：分页归一化（照抄管理端 `src/utils/pageResult.ts`）
- 输入可能是 `{ list, pagination }`、`{ content, total, page, pageSize }` 或纯数组。
- 统一输出 `{ list, pagination: { page, pageSize, total, totalPages } }`。
- 不做归一化 → 换一种后端返回结构就会翻页失败 / 白屏。
