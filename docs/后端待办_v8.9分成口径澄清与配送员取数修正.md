## A1. 配送员报酬：修正 `DeliveryService.resolveCourierEarning`

### A1.1 现状 vs 目标

| | 取数来源 | demo 公司（配送抽成 10%）实得 |
|---|---|---|
| **文档 / 开关 / 场景图**（三方一致） | `配送结算基数 × (1 − platform_delivery_share_rate)` | 10 × 90% = **9.00** |
| **代码实际**（孤儿逻辑） | `DeliveryRule.courierPerOrder`（`delivery_rules.courier_per_order` = 0.35，demo 覆盖 0.40） | **0.35 ~ 0.40** |

`DistributionProperties.courierShareFromDeliveryFee = true`（B 方案）已开，但 `resolveCourierEarning` 未跟随该开关，仍读固定每单金额。

### A1.2 建议改法

```text
deliverySettlementBase  = 实付配送费 + 配送补贴                    // 已实现
platformDeliveryShare   = deliverySettlementBase × platform_delivery_share_rate
courierEarning          = deliverySettlementBase − platformDeliveryShare
                        // 恒等式：deliverySettlementBase = platformDeliveryShare + courierEarning
```

1. `resolveCourierEarning` 改为按上式取 `property_companies.platform_delivery_share_rate`，不再读 `DeliveryRule.courierPerOrder`。
2. `delivery_rules.courier_per_order`、`property_companies.delivery_courier_per_order`、`courier_share_rate` **保留列不删**，标注「历史兼容 / B 方案下不再参与分账」，避免破坏存量数据与旧接口契约。
3. 兼容字段 `courierShare` 必须继续 ≡ `courierEarning`（文档 §配送结算已明确 `courierShare` 为兼容别名）。
4. 前置：本项直接影响配送员实收，**属产品决策，动手前请产品确认**。

### A1.3 影响面（改完需一并回归）

- `PendingDeliveryItemResponse.courierEarning`（待抢单 / 可抢单列表）
- 配送任务详情、配送结算详情中的 `courierEarning`、`platformDeliveryShare`
- `distribution_records` 配送侧金额（若有 `courier_amount`）
- 分账统计 `summary.courierAmount`、`summary.platformDeliveryAmount`
- 兼容字段 `courierShare`

> 影响范围提示：仅 `platform_delivery_share_rate > 0` 的公司（当前库中只有 demo 万达花园 = 10%）行为变化；其余公司抽成为 0，配送员仍拿全额 10.00。

## B1. 电商模式「平台」分成口径（账目矛盾，必须澄清）

### B1.1 矛盾点

后端回复表格中「平台 = 0」，但按 demo 公司配置 `platform_share_rate = 10%`，商品链路的平台分成应为：

```text
10（抽佣基数）× 10%（platform_share_rate） = 1.00
```

反推证据出自后端自己的表格：管理盘 **2.99 = 10 − 物业 6.01 − 1.00**，说明 1.00 在计算中**已被扣除**；但账面上记 0，导致：

```text
6.01（物业毛） + 2.99（管理盘） + 0（平台） = 9.00 ≠ 10.00    ← 差 1.00，账不平
```

### B1.2 请后端明确三点

1. **`distribution_records` 是否落 `platform_share = 1.00`（商品链路）？** 若落 0，这 1.00 记到哪张表、靠什么平账？
2. **`summary.platformAmount`（公司商品收入）应为 1.00 还是 0？**
3. **两条路径的平台收入是否一致？** 电商收付通下平台先拿「佣金 + 配送费 − 配送员收入」= 1.00 + 10.00 − 9.00 = 2.00；普通分账路径平台 = 商品 1.00 + 配送 1.00 = 2.00。请确认两路径最终一致，避免同单不同模式平台收入不等。

### B1.3 前端依赖（后端定口径后前端无需改码）

- `DistributionRecordsTable` 的「平台」列 → 读 `distribution_records.platform_share`
- `DistributionStats` 的「公司商品收入」卡 → 读 `summary.platformAmount`
- 「公司配送收入」卡 → 读 `summary.platformDeliveryAmount`（文档已明确与 `platformAmount` 分开统计、不得合并）

## D. 端到端验证用例（建议后端自测）

**环境参数**（demo 公司 `pc_demo001`）：物业 60.1% / 管理盘 29.9% / 平台 10%；板块抽管理盘 60% / 个体抽板块 50%；配送抽成 10%；商家抽佣 10%；楼长比例 10%

**场景**：商品 100 元 + 配送费 10 元，大厅配送，无积分 / 物业币抵扣，无满额减免

| 角色 | 期望所得 | 计算式 |
|---|---|---|
| 商家 | 90.00 | 100 − 抽佣 10 |
| 物业（净） | 5.41 | 6.01 − 楼长 0.60 |
| **单元楼长** | **0.60** | 6.01 × 10%（下单快照） |
| 统筹 | 1.20 | 2.99 − 板块毛额 1.79 |
| 板块负责人 | 0.89 | 1.79 − 个体 0.90 |
| 个体负责人 | 0.90 | 1.79 × 50% |
| 平台（商品） | 1.00 | 10 × 10%（**待 B1 确认**） |
| 平台（配送） | 1.00 | 10 × 10% |
| 配送员 | 9.00 | 10 × (1 − 10%)（**A1 改码后**） |
| **合计** | **110.00** | = 用户实付 ✅ |

## E. 回归检查点（改完 A1 / 定完 B1 后逐条验证）

| # | 校验 | 等式 |
|---|---|---|
| E1 | 配送侧守恒 | `deliverySettlementBase = platformDeliveryShare + courierEarning` |
| E2 | 物业侧守恒 | `物业净分成 + 楼长分成 = property_share_rate × 抽佣基数` |
| E3 | 管理盘内守恒 | `统筹 + 板块毛额 = 管理盘` 且 `个体 + 板块 = 板块毛额` |
| E4 | 一级三档守恒 | `物业毛 + 管理盘 + 平台商品 = 抽佣基数`（即 B1 的 1.00 必须落位） |
| E5 | 总额守恒 | 全角色合计 = 用户实付（含配送费） |
| E6 | 模式一致性 | 同一订单，普通分账 vs 电商收付通，五角色分项与平台收入完全一致 |
| E7 | 快照不回改 | 修改楼长比例 / 撤销楼长后，已有订单分成金额不变 |
| E8 | 兼容字段 | `courierShare` ≡ `courierEarning` |
| E9 | 各公司隔离 | 抽成为 0 的公司，配送员仍为全额；楼长扣除只影响其所属物业 |
