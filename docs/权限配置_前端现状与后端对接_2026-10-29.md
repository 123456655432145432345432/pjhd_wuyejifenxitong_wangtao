# 权限配置 — 前端现状与后端对接说明

> **提出方**：前端（邻里商城服务管理端，Vue3 + TS）
> **日期**：2026-10-29
> **依据**：`API接口文档_v8.25.md` §48 管理端—权限管理；本仓 `src/views/Permission.vue`、`src/stores/permission.ts`、`src/api/services.ts`、`src/router/index.ts`、`src/constants/roles.ts`、`src/constants/menus.ts`
> **性质**：本文档 = 前端现状陈述 + 需要后端确认的契约问题。**不含任何后端/SQL 结论性判断**，凡涉及后端行为的一律标为「待确认」。

---

## 0. 一句话结论

**权限配置目前只实现了"配置端"，没有实现"消费端"。**

- 配置端（页面 + 接口 + 权限池 + 预设 + 日志）前端已完整接通，`grant / revoke` 真实落库。
- 消费端（菜单、路由、按钮）**完全没有读权限码** —— 全站准入判定至今只看 `role` / `propertySubRole` / 标签（`isBuildingLeader` 等）。
- 所以「给某个角色/账号加上『参数配置』权限 → 用该角色登录 → 看不到参数配置页」**是必然结果，不是偶发 bug，也不是配置没保存成功**。

## 2. 为什么"配了也没效果"——三层原因（按优先级）

### 原因 1（根因）：前端全站准入只认角色，不认权限码

| 判定点 | 代码位置 | 依据字段 |
|---|---|---|
| 侧栏菜单 | `components/AppSidebar.vue` L74 → `getMenusForProfile(auth.profile)` | `role` / `propertySubRole` / 复合身份标签 |
| 路由守卫 | `router/index.ts` L950–962 | `meta.roles` + `getEffectiveRoles(profile)` |
| 领导专属二次校验 | `roles.ts` L393 `canAccessLeaderOnlyRoute` | `isPlatformAdmin` / `isPropertyLeader` |
| 按钮级 | —— | **不存在**（无 `hasPermission()`，无 `v-permission` 指令，无 directives 目录） |

`grep` 全仓结果：`permissionApi` 仅在 `stores/permission.ts`（即权限配置页自身）被引用；`effectivePermissions` / `permissionCodes` 在后端响应被解析后，**没有任何其他模块读取**。

**结论**：给账号授予任意权限码，前端的菜单不增加、路由不放开、按钮不出现。授权操作在 UI 上 100% 无感知。

### 原因 2：权限配置页本身只对两个管理员角色开放

- 路由 `permission`：`router/index.ts` L276–280
  ```
  roles: [platform_admin, property_admin] + propertyLeaderOnly: true
  ```
- 同规则也作用于 `param`（参数配置）：L339–343，`propertyOperatorMenus` 还把它从操作员菜单里剔除（`menus.ts` L85–100、L113–115）。
- 后端 §48.1 / §48.2 / §48.3、§48.7 / §48.8 的 Roles 同样写死为 `platform_admin` / `property_admin`（grant/revoke 甚至只写 `platform_admin`）。

**结论**：商户、配送员、统筹、板块、个体、组长、技工、住户这些业务角色，**既进不了权限配置页，也不在可被配置的范围内**。如果本次测试是用业务角色账号登录去看「参数配置」，那前端在路由层就会把请求弹回首页，与权限码无关。

### 原因 3：账号列表口径不明（待后端确认）

§48.1 的示例响应只有 `platform_admin` 与 `property_admin` 两条，`total: 2`。
若 `GET /admin/users` 实际只返回管理端账号，则权限配置的作用域仅为「两个管理员角色之间微调」，业务角色无法被授权 —— 这个功能就没有承载业务价值。

## 3. 前后端契约不一致（需后端澄清，按风险排序）

### P0-1｜权限码格式在文档内自相矛盾

| 出现位置 | 示例 code | 格式 |
|---|---|---|
| §48.2 权限列表 | `resident:read`、`merchant:audit`、`reports:view` | `模块:动作` |
| §48.6 用户权限 effectivePermissions | `resident:read`、`merchant:audit` | `模块:动作` |
| §48.7 grant 请求体 | `merchant:audit`、`reports:view` | `模块:动作` |
| **§48.3 角色预设 permissionCodes** | **`permission.resident.read`**、`permission.merchant.audit` | **点分 + `permission.` 前缀** |
| **§48.4 创建预设请求体** | **`permission.resident.read`** | **点分 + `permission.` 前缀** |

**前端影响（真实风险，不是理论问题）**：
`applyPreset` 会把预设里的 code 直接拿去和权限池的 code 做 `Set.has()` 比对（`mappers.ts` L700–717）。若两套格式不同：

1. 点完预设 → 所有复选框**全部勾不上**（用户看到的是"点了没反应"）；
2. 此时点保存 → `current = []`、`original = 原有 N 项` → 前端会向 revoke **提交该账号的全部现有权限**（`stores/permission.ts` L210–222）。

即：**格式不一致时，"套用预设"会变成"清空权限"**。请后端明确唯一编码规范（建议统一为 §48.2 池子返回的那个），并确保 `role-presets.permissionCodes` 与 `/admin/permissions` 的 `code` 是同一套字符串。

### P0-2｜property_admin（领导）能进页面、能勾选，但保存必然 403

§48.7 / §48.8 的 Roles 只写了 `platform_admin`。而 §48.1 / §48.2 允许 `property_admin`。
前端当前对领导开放保存按钮 → 领导点保存会拿到权限不足。

**需确认**：`property_admin` 是否允许 grant/revoke？
- 若允许 → 请补文档 Roles；
- 若不允许 → 前端改为「领导只读、隐藏保存与勾选」，请后端在 `GET /admin/users/{id}/permissions` 或账号列表里下发可用标志位（如 `canManage: boolean`），避免前端靠角色硬编码猜。

### P0-3｜权限码覆盖哪些接口？前端无法判断

文档 §0 说明：`SecurityFilterChain` 为 `anyRequest().permitAll()`，只有 `/admin/**` 额外过 `PermissionInterceptor` 做权限项校验。

而前端大量业务接口并不在 `/admin/**` 下，例如：
- 参数配置页部分请求走 `PATCH /admin/property-companies/{id}/config`（在 `/admin` 内，可能受权限码管）
- 但 `GET /property-companies`（`services.ts` L1008–1023）不在 `/admin` 内（大概率不受权限码管）

**需确认**：每个权限码到底保护哪些接口？如果权限码只保护 `/admin/**`，那前端即使做了菜单门控，也会出现「前端放开了页面 → 页面里的非 /admin 接口也照常能调」的反差；反之若后端对非 /admin 接口做角色硬校验，前端放开页面只会得到 403 空页。**这是能否真正落地权限码驱动的前提。**

### P1-1｜登录态里没有当前用户的权限码

`GET /auth/profile`、`POST /auth/admin-login` 的响应（前端 `types.ts` L23–34、L36+）都**没有** `permissions` / `effectivePermissions` 字段。
前端因此无法在登录后得知「我能看哪些页」，只能靠角色推。

**建议**（二选一，请后端定）：
1. `profile` / `admin-login` 响应增加 `permissions: string[]`（推荐，前端可零额外请求做门控）；
2. 新增 `GET /auth/my-permissions`，前端登录后拉一次并缓存。

注意：若走方案 1，需说明 `/auth/profile` 仅 `resident` / `property_admin` / `platform_admin` 可调（文档已写明 merchant、courier 调用返回 20004），因此 **merchant / courier / technician 这类角色仍拿不到权限码**，需要方案 2 覆盖，或让 admin-login 响应直接带回。

### P1-2｜权限码 ↔ 前端页面 缺少映射表

后端返回的是「模块:动作」语义（如 `resident:read`、`reports:view`），前端页面是按路由名组织的（`resident`、`param`、`permission`、`merchant-onboarding-approval` …，共 100+ 条）。
**两边现在都没有这张映射表**，这正是"配置端有、消费端无"的结构性原因。

**请后端提供**：每个权限码对应的前端页面/操作清单（可以是粗粒度：一个页面一个码，也可以细化到"查看/新增/审批"）。前端拿到后即可：
1. 生成 `permissionCode → routeName` 常量表；
2. 菜单过滤 `getMenusForProfile` 追加权限码过滤；
3. 路由守卫追加权限码校验；
4. 按钮级 `v-permission` 指令。

在此之前前端不宜自行猜测映射，否则会和后端校验口径打架。

### P2-1｜应用预设后 presetId 不会回写

前端保存只提交 grant/revoke 的差异码，**不提交 `rolePresetId`**。所以：
- `GET /admin/users/{id}/permissions` 返回的 `rolePresetId` 永远停留在旧值；
- 用户套用预设后，页面再次进入仍显示旧预设名。

**请确认**：是否需要"账号绑定预设"能力？若需要，请提供 `PUT /admin/users/{id}/role-preset`（或允许 grant 请求体带 `rolePresetId`）。若不需要，前端将去掉预设高亮显示，避免误导。

### P2-2｜reason 未采集，日志内容较薄

grant / revoke 接口都支持 `reason`，前端目前没有输入框、不传该字段，导致变更日志只能显示「授予权限 / 撤销权限」而无法说明原因。
**需产品确认**是否要求填写授权原因；若要求，前端加输入弹窗即可（无需后端改动）。

## 5. 当前可执行的验收路径（不依赖消费端改造）

想验证"配置是否真的落库"，请按下面顺序测，可绕开"看不到页面"的困惑：

1. 用 `platform_admin` 登录 → 进入「权限配置」；
2. 在「账号列表」里选中一个**目标账号**（先确认它在列表里，即该角色是否可被配置）；
3. 勾选若干权限项 → 点「保存权限」，看是否提示「权限已保存并立即生效」；
4. 刷新页面重新选中该账号 → 复选框应保持勾选状态（**这一步验证的是落库，不是生效**）；
5. 查看下方「权限变更日志」是否新增记录；
6. 用该目标账号重新登录 → **菜单与页面不会有任何变化**（这是当前预期行为，不是失败）。

> 若第 4 步勾选丢失、或第 3 步报 403 / 10002，才是真正的前后端 bug，请把响应体发前端。

### 7.2 落地方式（关键设计，请后端对齐）

1. **权限来源**：`GET /auth/my-permissions` → `permissions`；失败回落 `/auth/profile` 的 `effectivePermissions`；两处都拿不到则不启用门控。
2. **判定规则**（`stores/auth.ts` `hasPermission`）：
   - 未传权限码 → 放行（该页面/按钮未纳入门控）
   - `platform_admin` → 放行（与后端对超管的放行口径一致，也是配置误锁时的救援通道）
   - 权限未加载 / 为空数组 → 放行（**空数组视为「预设未配置」，不视为「全部撤销」**）
   - 其余 → 必须命中权限码
3. **声明式白名单**：只有 `ROUTE_PERMISSION` 登记过的路由/菜单才受权限码控制，未登记的维持「按角色放行」。这样在后端只覆盖 44 码的情况下不会把 30 多个无码页面隐藏掉。
4. **总开关**：`constants/permissionCodes.ts` 的 `PERMISSION_GUARD_ENABLED`，置 `false` 即整体退回纯角色控制。
5. **保存后刷新**：在权限配置页改了**自己**的权限，保存成功后立即重拉 `/auth/my-permissions`，无需重新登录。
6. **无权限落地页**：新增 `/403`（`views/Forbidden.vue`），展示所需权限码，而不是静默弹回首页。

### 7.5 请后端联调时确认

1. `GET /auth/my-permissions` 对 `property_leader`（`role=property_admin` + `propertySubRole=property_leader`）实际返回的 `permissions` 是否包含 `permission:read` / `config:set`。**若不含，领导将看不到权限配置与参数配置页**（这是本轮唯一的自锁风险点）。
2. 空数组语义确认：前端把 `permissions: []` 当作「预设未配置 → 回落角色」，而不是「全部撤销」。若后端希望空数组表示"零权限"，请明确，前端会改判定。
3. 44 个码之外，上表 7.4 的 30 个页面是否计划补码；若补，给出码名后前端只需在映射表加一行。
