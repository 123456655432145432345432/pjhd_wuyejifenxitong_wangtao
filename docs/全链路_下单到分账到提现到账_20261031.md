### 0.2 不在参数配置页的两个关键参数（容易找错地方）

| 参数 | 在哪改 | 影响链路哪一段 |
| --- | --- | --- |
| `platformDeliveryShareRate`（配送费抽成，默认 10%） | **平台分成配置**页 → `PUT /admin/platform-share-rates` | 配送费怎么在平台和配送员之间分 |
| `commissionRate`（商家佣金率） | **商家挂接配置** / 价格审批（`itemType=merchant_distribution`），审批通过才生效 | 商品价里平台盘占多少 |

验收时如果在参数配置页找这两个，会找不到——它们本来就不在那一页。

### 0.3 三个仍需注意的点

1. **物业领导的预设必须含 `coin:display_control`**，否则参数页那个展示开关不会渲染（不是 403，是不画）。这是权限收紧后的副作用，等后端核对预设。
2. **`deliveryBaseFee`（配送起步价）没有计费消费方**，后端明确它只用于平台商家利润测算，前端文案已改成「利润测算参考值」，不参与住户实际配送费。
3. **`pointToFeeRate`（积分抵现率）的消费方后端未明确说明**。字段能写、能回显，但积分抵扣在支付试算里实际用哪一档，文档里没写死。建议用一个积分单实测确认，不要按页面值推断。

## 1. 全链路一张图

```
① 下单          ② 支付            ③ 履约              ④ 记账分账         ⑤ 真实资金         ⑥ 提现
POST /orders → POST /pay → 配送/核实/自提 → distribution_records → 收付通分账/转账 → 审核+打款

金额快照        拆积分/币/现金     delivery_fee      钱包账本          平台佣金入账        扣余额
（后端算）      （防篡改）         settlementBase    wallet_flows      商家货款解冻        出款到零钱/银行卡
                                                                                        凭证归档
```

**两条线必须分开看**：

- **记账线**（④）：`distribution_records` + `wallet_flows`，决定每个人「看到多少钱」；
- **资金线**（⑤）：微信收付通，决定钱「实际怎么走」。

两者不是同一时点、也不是同一路径。**记账有余额 ≠ 钱已到账**，这是最容易出误解的地方。

## 2. 阶段 ①：下单（金额在这里就被锁死）

### 2.1 接口

```
POST /orders                     普通商家单
POST /orders/from-listing        业主上架商品（小店）
POST /orders/preview             支付试算（物业币商城规则）
POST /orders/from-listing/preview
POST /cart/delivery-fee          购物车运费预估
```

### 2.2 关键：金额快照由后端算，前端只渲染

创建订单返回的就是快照，后续所有环节读这份快照，**不重算**：

| 字段 | 含义 |
| --- | --- |
| `productAmount` | 商品金额（不含配送费，满额判断口径） |
| `deliveryFee` | 住户实付配送费 |
| `originalDeliveryFee` | 满额减免前的基础配送费 |
| `deliveryWaiverAmount` | 满额减免金额 |
| `deliverySubsidySponsor` | 减免承担方 `none`/`merchant`/`property`/`platform` |
| `deliverySettlementBase` | **配送结算基数**（实付 + 补贴），配送员收入按它算 |
| `totalAmount` | `productAmount + deliveryFee` |

同时落库两个隐藏快照：`orders.building_leader_id` / `building_leader_rate`——楼长分成在**下单那一刻**就绑定了，之后换楼长不影响旧单。

### 2.3 三类订单的差异（影响后面所有环节）

| 类型 | 判定 | 履约 | 配送费 | 结算触发 |
| --- | --- | --- | --- | --- |
| 普通配送单 | 默认 | 抢单配送 | 有 | 确认收货 |
| 团购单 | 所有商品 `category=团购` | 无需配送，商家核实 | 0 | 核实通过 + 冻结期 |
| 食堂单 | `merchant_type=canteen` | 无需配送 | 0 | 支付成功即 `completed` |
| 业主小店单 | `merchant_source=resident_shop` | 按小店配置（默认配送费 0） | 0 | 确认收货，走件数制 |

## 3. 阶段 ②：支付（四种方式，混合支付）

### 3.1 接口

```
POST /orders/{id}/pay
  { paymentMethod, pointUsed, coinUsed, wechatPayCode, openid,
    familyId, userCouponId, mainMerchantId, directedBalanceUsed }
```

| `paymentMethod` | 说明 |
| --- | --- |
| `point` | 纯积分（v8.11 起前端固定传 `pointUsed=0`，积分入口已移除，后端逻辑保留） |
| `property_coin` | 纯物业币 |
| `wechat` | 纯微信（电商收付通） |
| `mixed` | 混合：积分/物业币/定向余额/优惠券 + 微信补差 |

### 3.2 两种返回形态，别当成失败

| 情况 | 返回 | 处理 |
| --- | --- | --- |
| 积分 / 物业币 / 开发模式 | 无 `payParams`，`orderStatus` 直接 `paid` | 直接进下一阶段 |
| 微信 / 含现金的混合 | 返回 `paymentRecordId` + `payParams`，`orderStatus` 仍是 **`pending`** | **属正常**，调起 `wx.requestPayment`，回调后变 `paid`；前端轮询 `GET /orders/{id}`，60s 未确认给「我已支付」兜底 |

### 3.3 失败码（会直接影响链路走向）

| 码 | 含义 | 链路后果 |
| --- | --- | --- |
| `99004` | 商家未完成微信进件 | **不能微信支付**，只能回退积分/物业币 |
| `99003` | 电商收付通未配置/未启用 | 同上 |
| `97070` / `97071` | 本小区未启用积分 / 物业币 | 该支付方式不可用 |
| `60006` | 商家在该物业下未完成挂接配置 | 无法下单（无 `commissionRate` 就无法分账） |
| `80025` / `80026` / `80027` | 定向余额不足 / 越权 / 未选主商家 | 混合支付失败 |

> `60006` 是链路源头卡点：**商家没在物业下挂接，就分不了账**，所以下单和支付都会校验。

### 3.4 支付成功时立刻发生了什么

不是「钱到商家」，而是三件事同时落库：

1. 订单置 `paid`，扣积分/物业币/优惠券；
2. **生成分账记录**（团购/食堂单除外，见阶段 ④）；
3. 写 `wallet_flows` 流水：商家商品收入、商家承担补贴（负）、平台/物业/管理盘各级、平台配送收入。

**注意：此时余额是「待结算」，不是可提现。** 要等确认收货。

## 4. 阶段 ③：履约（决定什么时候结算）

### 4.1 三条路径

| 路径 | 接口 | 结果 |
| --- | --- | --- |
| 配送（主路径） | `POST /deliveries/{id}/grab` → `/complete` | 订单停在 `delivering` + `deliveredAt`，**不自动完成** |
| 居民确认收货 | `POST /orders/{id}/confirm` | 订单 `completed`，**触发分账结算** |
| 超期自动确认 | 每小时调度 `OrderAutoConfirmScheduler` | 已送达超过售后窗口（默认 3 天）自动完成并结算 |
| 商家手动完成 | `PATCH /orders/{id}/status` → `completed` | 同确认收货（管理兜底） |
| 团购单 | `POST /merchants/my/orders/{orderId}/verify` | 通过 → `verified` → 冻结期（默认 7 天）→ 自动结算 |

### 4.2 两个容易踩的点

**（1）配送员点「送达」≠ 订单完成。**
`courier` 角色不允许把订单置 `completed`（返回 `70002`）。送达只写 `deliveredAt`，订单还停在 `delivering`。

**（2）配送员的钱和结算无关。**
`POST /deliveries/{id}/complete` 一成功，`courier_delivery_income` 立刻入账，钱与订单是否确认收货无关。而商家货款、四级分成、楼长分成都要等 `completed`。

这就是 v8.10 修的那个洞：骑手送达后如果买家一直不确认收货，分成永远不落账，但配送费已经付出去了。所以补了自动确认任务。

### 4.3 `completed` 是资金终态

一旦置 `completed` 即触发微信分账冻结，**不再支持线上退货退款**。退款只能发生在 `paid` / `delivering` 阶段。

## 5. 阶段 ④：分账记账（钱「记」给谁）

### 5.1 两线拆分（B 方案）

```
订单实付 totalAmount = productAmount（商品价） + deliveryFee（配送费）
│
├─【商品价线】
│   ├─ 商家 merchantShare = productAmount × (1 − commissionRate)
│   └─ 平台盘 distributableAmount
│        = productAmount × commissionRate − pointCost − coinCost
│        ├─ 我们公司  platformShare       （默认 10%）
│        ├─ 物业      propertyShare       （默认 60%）
│        │    └─ 楼长 buildingLeaderShare = propertyShare × building_leader_rate
│        └─ 管理盘    coordinatorShare 池  （默认 30%）
│              ├─ 统筹 coordinatorShare
│              ├─ 板块 sectorLeaderShare
│              └─ 个体 individualLeaderShare
│
└─【配送费线 · 独立】
    ├─ 我们公司 platformDeliveryShare = deliverySettlementBase × platformDeliveryShareRate
    └─ 配送员   courierShare = courierEarning = deliverySettlementBase × (1 − 该比例)
```

### 5.2 四条铁律

1. **平台盘不含配送费**。配送费只在我们公司和配送员之间分，物业/统筹/板块/个体不碰配送费。
2. **配送员无保底**。旧 A 方案的 `clamp(平台盘×15%, 0.6, 5)` 已废弃，现在只跟配送费走，所以不会出现「平台盘 0.48、配送员硬拿 0.6」的倒贴。
3. **积分/物业币成本先从平台盘扣**。全额积分或全额物业币支付时，平台盘可能为 0，各级现金分成为空——这是预期，不是 bug。
4. **楼长分成从物业那份里扣**，不是额外加一笔：`propertyShare` 相应减少，总额守恒，不影响统筹/板块/个体。

### 5.3 数字示例（便于验收口述）

商品 10 元 + 配送 1 元、`commissionRate=0.10`、平台盘 1:6:3、配送抽成 10%、楼长费率 10%：

| 项 | 金额 |
| --- | --- |
| 商家 | 10 × 0.9 = **9.00** |
| 平台盘 | 10 × 0.1 = **1.00** |
| └ 我们公司 | 0.10 |
| └ 物业 | 0.60 → 楼长 0.06 / 物业实留 **0.54** |
| └ 管理盘 | 0.30 → 统筹 0.12 / 板块 0.09 / 个体 0.09 |
| 配送费 · 我们公司 | 1 × 0.1 = **0.10** |
| 配送员 | **0.90** |

校验：`0.10 + 0.60 + 0.30 = 1.00`（平台盘守恒）；`0.10 + 0.90 = 1.00`（配送费守恒）。

> ⚠️ 文档有两处默认值不一致：B 方案写 `propertyShareRate=60%`，§99（v8.9）写「有统筹时 `property_share = 可分配金额 × propertyRate`，默认 0.30」。**以接口实际返回为准**，不要用文档数字手工对账。已列入待确认。

### 5.4 业主小店：完全不参与四层分账

`listing` 订单跳过 `DistributionService`，走件数制：

```
零售价 P，进货价 W，件数 Q，佣金率 R（默认 0.10）
商品额     = P × Q
一级代理货款 = W × Q    → 一级代理商家钱包（distributor_wholesale_income）
平台佣金    = 商品额 × R
店主差价    = 商品额 − 货款 − 佣金 → 业主卖货钱包（reseller_profit）
```

差价不参与物业/统筹/板块/个体/楼长分成。**这是两条完全独立的分账路径**，验收时要分开测。

### 5.5 账本：`wallet_flows`

每次结算、配送结算、退款冲正都在同一事务里写一条不可变流水，幂等键防重：

```
distribution:settle:{orderId}:{entryType}:{ownerType}:{ownerId}
delivery:settle:{deliveryId}
distribution:reverse:{orderId}:{entryType}:{ownerType}:{ownerId}
```

流水不删不改，冲正靠负数流水 + `refRecordId` 指回原流水。这是**官方审计账本**，对账以它为准。

## 6. 阶段 ⑤：真实资金流（钱实际怎么走）

### 6.1 电商收付通模式（现网）

```
住户付款 ──直连──▶ 商家二级商户号 sub_mchid     ← 资金不经过平台账户
                        │
                        ├─ 平台发起分账（冻结）
                        │    ├─ 平台佣金 ──▶ 平台商户号
                        │    └─ 配送费   ──▶ 配送员 openid（需预授权）
                        │
                        └─ 售后窗口到期 → finish → 剩余货款解冻给商家
```

**关键差异**：改成收付通后，平台不再归集货款（消除了二清风险）。所以「商家收到钱」有两条相反的路径：

- 微信单：货款在商家自己的二级商户号里，平台只是**分走佣金**，剩下的解冻给商家；
- 积分/物业币单：没有微信资金流，纯粹记账。

### 6.2 四层分成树不走微信分账

物业 / 统筹 / 板块 / 个体 **不在微信分账链路里**。流程是：

```
平台佣金到账平台账户 → 微信商家转账（新版）→ 各角色绑定的零钱 / 银行卡
```

这是**平台内部结算**，合规上不算二清。所以：

- 这些角色必须先绑「我的收款方式」（`/admin/cbk/accounts` 体系，微信零钱 openid 或银行卡）；
- 没绑 = 记账上有钱，但打不出去。

### 6.3 这条线目前的成熟度（重要）

`docs` 里两处明确写着：真实打款参数待微信侧确认，原 `AutoWithdrawalService` 等占位打款代码已移除，避免被误认为「提现已接入」。

**结论：当前提现到账是「记账 + 人工打款」，不是全自动出款。** 见阶段 ⑦。

## 7. 阶段 ⑥：各角色钱包与可提现口径

统一公式：

```
可提现 = 累计收益 − 已提现(completed) − 在途(pending + approved)
（负数置 0）
```

| 角色 | 钱包接口 | 可提现来源 |
| --- | --- | --- |
| 商家 | `GET /merchants/my` → `withdrawableAmount` | 商品收入 − 配送补贴承担 |
| 配送员 | `GET /courier-managers/my` | 配送费收入，送达即入账 |
| 统筹 | `GET /coordinators/my` | 管理盘分成 |
| 板块负责人 | `GET /sector-leaders/my` | 管理盘分成 |
| 个体负责人 | — | 累计分成 − 已占用 |
| 物业 | `GET /admin/property-companies/{id}/settlement-balance` | `propertyShare` − 楼长分成 |
| 物业经理 | `GET /property-managers/my/wallet` | 抽成收益 |
| 业主（卖货） | `GET /resident-merchants/seller-wallet` | 差价 `reseller_profit`，**仅可提现，不可消费、不可转物业币** |
| 技工 | — | 已完成 `service_orders` 金额合计 − 已提现 |

## 8. 阶段 ⑦：提现申请 → 审核 → 打款 → 到账

### 8.1 端点表

| 角色 | 申请 | 记录 | 审核入口 |
| --- | --- | --- | --- |
| 商家（含组长/技工） | `POST /merchant/withdrawals` | `GET /merchant/withdrawals` | `POST /admin/merchant-withdrawals/{id}/audit` |
| 配送员 / 多角色 | — | — | `POST /admin/role-withdrawals/{id}/audit` |
| 业主（卖货） | `POST /resident-merchants/seller-wallet/withdrawals` | 同前缀 GET | 同上（`withdrawal_type=resident_seller`） |
| 物业 | `POST /admin/property-companies/{id}/settlement-withdrawals` | 同前缀 GET | `.../{withdrawalId}/approve`、`/reject` |
| 物业币兑换现金 | — | — | `POST /admin/coin-withdrawals/{id}/audit` |
| 统筹 / 板块 / 个体 | `POST /{role}/{id}/withdrawals` | 同前缀 GET | `role-withdrawals` |

### 8.2 状态机（四态，多一步打款确认）

```
pending ──审核──▶ approved ──打款──▶ completed（终态）
   │                  │
   └──── rejected ◀───┘
```

| 当前 | 允许 | 说明 |
| --- | --- | --- |
| `pending` / `pending_audit` | `approved` / `rejected` | 首次审核；**不能直接 completed** |
| `approved` | `completed` / `rejected` | 打款完成或复核拒绝 |
| `rejected` / `completed` | — | 终态 |

### 8.3 打款环节的真相

`POST /admin/role-withdrawals/{id}/audit` 传 `auditResult=completed` 时，后端做的是：

```
disburseChannel = manual
disburseStatus  = success
completedAt     = now
transferProof   = 你上传的转账截图 URL
```

**也就是说：系统不发起转账，由财务线下打款，再把凭证回填。** `disburseChannel` 另一取值 `auto_cbk` 是给自动通道预留的，目前真实资金动作未启用。

这一点在验收话术里必须说清，否则会误以为「点完成 = 钱自动到账」。

### 8.4 手续费

- 提现手续费率 `withdrawalFeeRate` 在**参数配置**（仅平台可写），默认常见 6‰；
- 物业提现按物业公司自己的 `withdrawal_fee_rate`，没配就用平台默认物业类费率；
- 回显 `feeAmount` / `actualAmount`，住户看到的是扣完手续费的实到金额。

### 8.5 提现失败码

| 码 | 含义 | 前端处理 |
| --- | --- | --- |
| `94003` | 超额 / 可提现余额不足 | 禁止提交 |
| `94005` | `withdrawalBlocked`（未缴物业费等） | 金额置 0、置灰，提示「请及时缴纳物业费或联系管理人员」 |
| `20004` | 角色无提现权限 | — |

## 9. 逆向：退款与冲正

| 阶段 | 能否退 | 处理 |
| --- | --- | --- |
| `pending` 未支付 | 可取消 | 回补库存/件数、释放优惠券 |
| `paid` | 可退款 | 退积分/物业币/现金，恢复库存 |
| `delivering` | 可退款 | 同上 |
| `completed` | **不能** | 资金终态，只能走售后协商 |

退款时对原 `wallet_flows` 逐条生成负数 `distribution_reversal`，**不删除原流水**。业主小店退款额外做三件事：2 条负向流水、结算单置 `reversed`、`soldQuantity` 回退（卖完下架的自动重新上架）。

配送费退款有个特殊点：微信分账出去的配送费**不可回退**，由平台垫付并登记待追回台账（`/admin` 回退台账）。

## 11. 端到端验收：8 步走完一笔

前置：一个已进件商家（`commissionRate=0.10`）、一个配送员、平台盘 1:6:3、配送抽成 10%、物业有 active 楼长（费率 10%）。

| 步 | 操作 | 预期 |
| --- | --- | --- |
| 1 | 住户下单 商品 10 + 配送 1，微信支付 | 订单 `paid`，返回 `payParams`；支付后 `orderStatus` 短暂 `pending` 属正常 |
| 2 | 查 `GET /admin/distribution-records?orderNo=xxx` | 一条记录：`merchantShare=9.00`、`distributableAmount=1.00`、`courierShare=0.90`、`buildingLeaderShare=0.06` |
| 3 | 看商家钱包 | 9.00 在「待结算」，**不在可提现** |
| 4 | 配送员抢单 → 完成配送 | 订单停在 `delivering`；配送员可提现 **+0.90**（此时立刻入账） |
| 5 | 住户确认收货 | 订单 `completed`，商家 9.00 转可提现，各级分成落账 |
| 6 | 商家申请提现 5.00 | 状态 `pending`，`feeAmount=0.03`、`actualAmount=4.97` |
| 7 | 平台审核 `approved` → 财务线下打款 → 回填 `completed` + `transferProof` | 状态 `completed`，`disburseChannel=manual`、`disburseStatus=success`；商家可提现扣减 5.00 |
| 8 | 查 `wallet_flows` | 每个角色都有对应流水，幂等键唯一，无重复入账 |

**反向用例**（必须测，是 B 方案的核心）：

| 用例 | 做法 | 期望 |
| --- | --- | --- |
| 小平台盘不倒贴 | 高积分抵扣让平台盘 < 0.5，配送费仍 1.00 | 配送员仍拿 0.90，不出现保底 0.6 |
| 全额积分单 | 全积分支付 | 平台盘 0、各级现金分成 0，页面不报错 |
| 确认收货是唯一触发 | 送达后不确认收货，等自动任务 | 超售后窗口期自动 `completed` 并结算 |
| 楼长快照 | 下单后换楼长，再完成订单 | 分成仍给下单时那位楼长 |
| 小店隔离 | 业主小店下单 | 不进四层分成，只产生 `reseller_profit` + `distributor_wholesale_income` |

## 12. 已知边界（别当 bug 报）

1. **`completed` 后不能退款**，是设计，不是缺陷。
2. **微信单支付成功但状态还是 `pending`**，要等回调，60 秒内正常。
3. **积分/物业币全额单没有现金分成**，平台盘为 0 是预期。
4. **商家未进件不能微信支付**（`99004`），只能用积分/物业币。
5. **物业/统筹/板块/个体不参与配送费**，配送费只有平台和配送员两方。
6. **提现「完成」= 财务已线下打款并回填凭证**，系统不发起转账。
7. **四层分成树打款依赖角色绑定收款方式**，没绑就只能在账上看到钱。
