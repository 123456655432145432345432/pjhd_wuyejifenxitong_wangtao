# 分账 B 方案 · 测试流程 & 移动端对接说明

> 面向：测试 / 管理端联调 / 移动端（C 端 App）对接  
> 版本：2026-08-10（B 方案）  
> 依据：`docs/分账结构可视化.html` + 本仓管理端已落地口径  
> 废止：旧「A 方案（平台盘×15% + ¥0.6~¥5 保底）」作为现网主逻辑；仅作回退对照  
>
> **一句话铁律**：前端 / 移动端**只渲染后端返回的份额与金额**，**永不本地重算正式份额**；文案一律「待结算 / 可提现」，禁止「已到账 / 付款即到账」。

## 0. 相对旧文档的变更摘要

| 项 | A 方案（已弃用为主逻辑） | B 方案（现网） |
|----|--------------------------|----------------|
| 平台盘基数 | 订单实付 `totalAmount` | **商品价** = `totalAmount − deliveryFee`（或后端 `productAmount`） |

| 倒贴风险 | 平台盘 0.48 时仍保底 0.6 | **消除** |

## 1. 资金模型（必须背下来）

```
订单实付 totalAmount = 商品价 productAmount + 配送费 deliveryFee
│
├─【商品价线】
│   ├─ 商家 merchantShare ≈ productAmount × (1 − commissionRate)
│   └─ 平台盘 distributableAmount
│         ≈ productAmount × commissionRate − pointCost − coinCost
│         ├─ 我们公司 platformShare          （默认占平台盘 10%）
│         ├─ 物业     propertyShare          （默认 60%）
│         └─ 管理盘   coordinatorShare 池    （默认 30%）
│               ├─ 统筹本人（管理盘内再拆，默认约 40%）
│               ├─ 板块负责人 sectorLeaderShare
│               └─ 个体负责人 individualLeaderShare
│
└─【配送费线 · 独立】
    ├─ 我们公司 platformDeliveryShare ≈ deliveryFee × platformDeliveryShareRate（默认 10%）
    └─ 配送员   courierShare / courierEarning = deliveryFee − 平台抽成（无保底）
```

### 必记要点

1. **佣金比例可配**：`commissionRate` 按商家配置，含义仍是「商品价中平台盘占比」，**不是**把整笔订单都当平台盘。
2. **平台盘三档默认 1:6:3**，之和应为 100%：`platformShareRate` + `propertyShareRate` + `coordinatorShareRate`。
3. **管理内**默认用级联字段等价 4:3:3：`sector_leader_rate=0.6`、`individual_leader_rate=0.5`。
4. **配送费不进商家份额、不进平台盘**；物业 / 统筹 / 板块 / 个体**不参与**配送费分账。
5. **开关（后端）**：`courierShareFromDeliveryFee = true` 为 B；关掉可回退 A（联调时以环境开关为准）。
6. 全额积分 / 物业币支付 → 平台盘可能为 0，现金分成为空 —— **预期，不是 bug**。

### 数字示例（便于验收口述）

假设：商品 ¥10、配送费 ¥1、`commissionRate=0.10`、积分/币成本=0、平台盘三档 1:6:3、配送抽成 10%。

| 项 | 金额 |
|----|------|
| 商家 | 10 × 0.9 = **9.00** |
| 平台盘 | 10 × 0.1 = **1.00** |
| └ 我们公司 | 0.10 |
| └ 物业 | 0.60 |
| └ 管理盘 | 0.30 → 统筹 0.12 / 板块 0.09 / 个体 0.09 |
| 配送费·我们公司 | 1 × 0.1 = **0.10** |
| 配送员 | **0.90** |

> 图示左侧「商品 10 → 五分账合计 1」= **平台盘=1** 时的二次分，不是 10 元全进平台盘。

## 2. 移动端对接（B 方案）

### 2.1 红线（DO / DON'T）

| # | ✅ 必须 | ❌ 禁止 |
|---|--------|--------|
| 1 | 直接取后端 `*Share` / `courierEarning` / 钱包字段 | 用 `订单额×比例` / `平台盘×15%` 本地算正式金额 |
| 2 | 文案「待结算 / 可提现 / 预计可得」 | 「已到账 / 付款即到账 / 已分账」 |
| 3 | UI 状态由后端 `status` 驱动 | 本地累加余额、猜状态 |
| 4 | 分页兼容 `list` 与 `content` | 只解析一种结构 |
| 5 | 完成配送后**立刻**拉钱包接口刷新 | 用本单预计收入本地 `+=` |
| 6 | 配送员收入口径写「来自配送费」 | 再写「平台盘×15% / 保底 0.6~5」 |

### 2.2 分账明细

```
GET /distribution/records
    ?page=1&pageSize=20
    &orderId=&merchantId=
    &coordinatorId=&sectorLeaderId=&individualLeaderId=
    &propertyCompanyId=&startDate=&endDate=&sort=-createdAt

鉴权：登录；常见角色 coordinator / property_admin / platform_admin
管理端同结构：GET /admin/distribution-records
```

**分页兼容（必做）**

```
本仓：   { list: [...], pagination: { page, pageSize, total, totalPages } }
Spring： { content: [...], total, page, pageSize }
```

**字段（B 方案关注点）**

| 字段 | 含义 |
|------|------|
| `totalAmount` | 订单实付（商品+配送） |
| `productAmount` | 商品价（若返回；否则可用 `totalAmount − deliveryFee` 仅作理解，勿当正式重算） |
| `deliveryFee` | 配送费 |
| `commissionRate` | 商品价抽佣 / 平台盘占比 |
| `distributableAmount` | **平台盘**（已扣积分/币成本），**不含配送费** |
| `merchantShare` | 商家份额（按商品价） |
| `platformShare` | 平台盘内「我们公司」 |
| `propertyShare` / `coordinatorShare` / `sectorLeaderShare` / `individualLeaderShare` | 平台盘二次分 |
| `platformDeliveryShare` | 配送费中我们公司抽成（与 `platformShare` **不同链路**） |
| `courierShare` | 配送员收入（= 配送费余额），与任务 `courierEarning` 合轨 |
| `status` / `createdAt` | 状态 / 时间 |

**读取规则**

1. 份额优先 `*Share` → `*Amount` → snake_case。  
2. **按角色只显自己列**：商家只显 `merchantShare`；配送员侧看任务 `courierEarning` / 明细 `courierShare`。  
3. 防御性兜底可参考管理端 `src/utils/distribution.ts`，**正常路径不要依赖前端兜底**。

### 2.3 分账统计

```
GET /distribution/stats?startDate=&endDate=&dimension=summary&propertyCompanyId=
（管理端：GET /admin/distribution/statistics）
```

`summary` 直接展示，**勿本地 sum 明细**：

- `totalOrderAmount` / `merchantAmount`
- `totalDistributableAmount` / `platformAmount` / `propertyAmount` / …
- `courierAmount`（B：配送费侧配送员合计，不是平台盘×15%）

### 2.4 试算（商家「本单预计可得」）

```
GET /distribution/calculate
    ?merchantId=&totalAmount=&deliveryFee=&pointUsed=&coinUsed=&propertyCompanyId=
```

> `deliveryFee` 是否已支持以**后端最新文档**为准；若参数尚未放开，先传 `totalAmount`（含配送）并核对返回是否已拆 `deliveryFee` / `courierShare`。

返回关注：

- `commissionBaseAmount`、`distributableAmount`、`merchantShare`
- `courierShare`、`platformDeliveryShare`（有则展示）
- 文案：**「预计可得」**，非已到账

### 2.5 商家抽佣 `commissionRate`

- 语义：商品价中平台盘占比（按店配置）。  
- 变更走价格审批 `itemType = merchant_distribution`，**审批通过后生效**。  
- 展示时标注「审批通过后生效」。

### 2.6 配送员收入（B 方案 · 合轨）

**结论**：`courierEarning` ≡ `courierShare`（同一笔、同数值）。

**后端计算口径（移动端只展示，勿自己实现为正式逻辑）**

```
platformDeliveryShare = deliveryFee × platformDeliveryShareRate   // 默认 0.1
courierEarning        = deliveryFee − platformDeliveryShare       // 无下限、无上限
```

**展示**

- 抢单 / 任务：「预计收入」= `courierEarning ?? fee`  
- 副文案：「完成配送后计入可提现」；说明来自配送费，非平台盘  
- 禁止：按单固定 0.35、A 方案 15%/0.6~5

**入账触发**

```
POST /deliveries/{id}/complete  成功
  → 立刻 GET /courier-managers/my 刷新可提现（不要本地累加）
```

### 2.7 各角色提现（端点表）

统一规则：

- 金额 ≤ 可提现（后端校验；前端仅体验兜底）  
- 手续费常见 `feeRate = 0.006`（6‰）  
- 状态：`pending → approved → completed`（或 `rejected`）  
- 请求体通常 `{ "amount": number }`

| 角色 | 申请 | 记录 | 可提现来源 |
|------|------|------|-----------|
| 物业(分成) | `POST /admin/property-companies/{id}/settlement-withdrawals` | 同名 GET | `settlement-balance` |
| 商家 | `POST /merchant/withdrawals` | `GET /merchant/withdrawals` | `GET /merchants/my → withdrawableAmount` |
| 配送员 | `POST /courier-managers/my/withdrawals` | `GET /courier-managers/my/withdrawals` | `GET /courier-managers/my` |
| 统筹 | `POST /coordinators/{id}/withdrawals` | `GET /coordinators/{id}/withdrawals` | `GET /coordinators/my` |
| 区块 | `POST /sector-leaders/{id}/withdrawals` | `GET /sector-leaders/{id}/withdrawals` | `GET /sector-leaders/my` |
| 个体 | `POST /individual-leaders/{id}/withdrawals`（本仓或有 `me`） | 同前缀 GET | 累计分成 − 已占用 |

错误码：

| 码 | 处理 |
|----|------|
| `94003` | 超额，禁止提交 |
| `94005` | `withdrawalBlocked`：金额置 0、置灰；提示「请及时缴纳物业费或联系管理人员」 |

**B 方案常量（仅理解/示意，正式金额用后端）** — 对齐 `src/constants/courierEarning.ts`：

```typescript
export const DEFAULT_PLATFORM_DELIVERY_SHARE_RATE = 0.1

export function calcCourierEarningFromDeliveryFee(
  deliveryFee?: number | null,
  platformDeliveryShareRate = DEFAULT_PLATFORM_DELIVERY_SHARE_RATE
) {
  if (deliveryFee == null || Number.isNaN(Number(deliveryFee))) return undefined
  const fee = Number(deliveryFee)
  if (!Number.isFinite(fee) || fee < 0) return undefined
  const rate = Math.min(Math.max(Number(platformDeliveryShareRate) || 0, 0), 1)
  const platformCut = Math.round(fee * rate * 100) / 100
  return Math.round(Math.max(fee - platformCut, 0) * 100) / 100
}
```

## 3. 测试流程（建议按序执行）

### 3.0 前置条件

| 准备项 | 说明 |
|--------|------|
| 环境开关 | 确认 `courierShareFromDeliveryFee = true`（B） |
| 物业配置 | 平台盘三档约 1:6:3；`platformDeliveryShareRate` 默认 0.1 |
| 测试商家 | 已知 `commissionRate`（建议先用 0.10 便于心算） |
| 测试账号 | 商家、配送员、统筹/板块/个体（按需）、平台管理员 |
| 管理端入口 | 平台分成配置、参数配置、分成明细/统计、配送员任务/提现 |

### 3.1 冒烟：一笔标准现金单（商品+配送）

**步骤**

1. 业主下单：商品价明确、配送费 > 0（例：¥10 + ¥1），现金支付完成。  
2. 订单进入配送 → 配送员抢单 → `complete` 完成配送。  
3. 打开分成明细，定位该 `orderNo`。

**期望**

| 检查点 | 期望 |
|--------|------|
| 有分账记录 | 一条对应订单 |
| `deliveryFee` | ≈ 用户付配送费 |
| `distributableAmount` | ≈ 商品价 × commissionRate − 成本（**不含**配送费） |
| `merchantShare` | ≈ 商品价 × (1 − commissionRate) |
| `courierShare` | ≈ deliveryFee × (1 − platformDeliveryShareRate) |
| 平台盘各方之和 | ≈ `distributableAmount`（允许分位误差 0.01） |
| 配送费拆分 | `platformDeliveryShare + courierShare ≈ deliveryFee` |
| 文案 | 无「已到账」 |

**反例（应失败/报后端）**

- `courierShare` 仍被抬到 0.60，而 `deliveryFee × 0.9` 更小 → 仍在走 A 保底。  
- `courierShare` ≈ `distributableAmount × 0.15` → 仍在从平台盘切。

### 3.2 小平台盘 / 倒贴回归（B 核心）

**目的**：验证不再出现「平台盘 0.48、配送员仍拿 0.6」。

**步骤**

1. 构造小商品额或高积分抵扣，使 `distributableAmount` 很小（如 < 0.5），但 `deliveryFee` 仍为正常值（如 1.00）。  
2. 完成配送，对比 `courierShare` / `courierEarning`。

**期望**

- 配送员收入只跟配送费与抽成走，**与平台盘大小无关**。  
- 不出现配送员收入 > 平台盘且被硬保底到 0.6 的倒贴形态。

### 3.3 配送员三处合轨

同一笔已完成配送订单：

| 位置 | 字段 | 期望 |
|------|------|------|
| 分成明细 | `courierShare` | = X |
| 配送任务 | `courierEarning` | = X |
| 完成前后钱包 | `GET /courier-managers/my` 增量 | ≈ X（勿本地累加） |

异常：「明细 0.90、钱包只加 0.35」→ **报后端未合轨**。

### 3.4 零配送费 / 自提（若业务支持）

- `deliveryFee = 0` → `courierShare` / `platformDeliveryShare` 应为 0。  
- 平台盘仍只按商品价走。  
- 页面不报错、不展示假保底。

### 3.5 全额积分 / 物业币

- 平台盘与现金分成可为 0。  
- 若仍收配送费现金，配送费线仍应按 B 拆（以后端实现为准；若后端规定积分配送另议，记录实际行为）。

### 3.6 比例可调验收（管理端）

1. 平台管理员改 `platformDeliveryShareRate`（如 10% → 20%）。  
2. 新下一单（旧单不要求回溯）。  
3. 期望：新单 `courierShare = deliveryFee × 0.8`。  
4. 改平台盘三档（保持和为 100%），新单二次分比例跟随；校验三档和不满足时后端校验/前端告警。

### 3.7 角色视角抽检

| 角色 | 看什么 | 不应看到/不应计入 |
|------|--------|-------------------|
| 商家 | `merchantShare`、试算预计可得 | 把配送费算进自己份额 |
| 配送员 | `courierEarning`、可提现 | A 方案文案；从平台盘算收入 |
| 统筹/板块/个体 | 各自 `*Share`、提现 | 从配送费再分一笔 |
| 物业 | `propertyShare` / settlement | 配送费抽成进物业 |
| 平台 | `platformShare` + 配送费抽成统计 | 混成一列说不清 |

### 3.8 提现链路

1. 配送员 / 商家等余额足够 → 申请提现。  
2. 超额 → `94003`。  
3. `withdrawalBlocked=true` → 置灰 + 固定提示语。  
4. 回显 `feeAmount` / `actualAmount`（6‰）。

### 3.9 管理端页面回归清单

| 页面 | 检查 |
|------|------|
| 平台分成配置 | B 方案说明；配送费抽成可编；示意分平台盘与配送费两线 |
| 参数配置 · 送货/分账 | 无 A 方案 0.6~5 主文案；配送抽成指向平台分成配置 |
| 分成明细表 | Banner 为 B；快递收入列有值且合轨 |
| 分成统计 | 快递收入说明为配送费来源 |
| 商家订单试算 | 「快递收入(B·配送费)」；有则显示配送费·我们公司 |
| 配送员抢单/任务/提现 | 文案为 B，无保底叙述 |
