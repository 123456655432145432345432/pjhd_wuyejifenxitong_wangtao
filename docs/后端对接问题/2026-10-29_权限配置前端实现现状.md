# 权限配置：前端实现现状说明

> **状态**：供后端了解前端现状，非缺陷单
> **日期**：2026-10-29
> **配套文档**：[2026-10-28_权限配置未生效_权限码契约](./2026-10-28_权限配置未生效_权限码契约.md)（那份是向前端提出的契约诉求，本文只讲前端已做到哪一步）

## 一句话结论

**配置端（写）已完整实现并跑通；消费端（读）未实现，且不是漏写，而是登录态里根本拿不到权限码。** 前端全部准入只由 `role` + `propertySubRole` 决定，权限码不参与任何一处判断。

所以"给角色配了参数配置，登录后看不到参数配置"是当前实现的必然结果，与配置内容无关。

## 1. 权限配置页在哪、谁能进

| 项 | 值 |
| --- | --- |
| 路由 | `/permission`（`name: 'permission'`），`router/index.ts:276-280` |
| 路由 meta | `roles: [...ADMIN_ROLES]`（`platform_admin`、`property_admin`）、`propertyLeaderOnly: true` |
| 菜单项 | `menus.ts:27` `{ name: '权限配置', route: 'permission' }` |
| 组件 | `views/Permission.vue`，状态在 `stores/permission.ts` |
| 移动端 | `constants/mobilePortal.ts` 的 `buildAdminWorkbench` 复用 `getMenusForProfile`，准入结论一致 |

跨过两道闸才能进：

1. `canAccessRouteAny(effectiveRoles, ['platform_admin','property_admin'])` — 只看角色；
2. `canAccessLeaderOnlyRoute(profile, 'permission')` — 要求 `isPlatformAdmin() || isPropertyLeader()`。

`isPropertyLeader()` 的判定是 `role=property_admin` **且** `propertySubRole=property_leader`。因此**物业操作员进不去**，且被静默重定向回首页（`router/index.ts:958-962`），不弹提示、不报 403。

## 2. 页面做了哪四块

| 区块 | 数据来源 | 说明 |
| --- | --- | --- |
| 角色快捷预设条 | `GET /admin/role-presets` | 按钮点一下把该预设的 `permissionCodes` 全量刷成勾选态（**仅前端态**，不写库，必须再点保存） |
| 账号列表 | `GET /admin/users?keyword&page&pageSize=20` | 滚动分页；每项显示姓名、角色中文名、脱敏手机号、`effectivePermissionCount` |
| 权限勾选区 | `GET /admin/permissions` + `GET /admin/users/{id}/permissions` | 左侧勾选态来自该账号的 `effectivePermissions`；支持关键字过滤 |
| 变更日志 | `GET /admin/permission-change-logs?userId&sort=-createdAt` | 表格（桌面）/ 卡片（移动）两套渲染 |

## 3. 数据流时序（实际执行顺序）

```
进入页面
 ├─ 并发：GET /admin/permissions          → 权限池（扁平数组）
 │        GET /admin/role-presets         → 预设列表
 ├─ 并发：GET /admin/users?page=1&pageSize=20
 │        GET /admin/permission-change-logs?page=1&pageSize=20
 ├─ 自动选中列表第一个账号
 │        → GET /admin/users/{id}/permissions
 │        → 用 effectivePermissions 回填勾选态，同时记下 originalEffective 作为基线
 ├─ 勾选/取消（纯本地 toggle，随时可"恢复当前生效"回到基线）
 └─ 点保存
      ├─ 计算差集：toGrant = 当前 − 基线；toRevoke = 基线 − 当前
      ├─ 无差集 → 提示"权限无变更"，不发请求
      ├─ toGrant 非空 → POST /admin/users/{id}/permissions/grant  { permissionCodes, reason }
      ├─ toRevoke 非空 → POST /admin/users/{id}/permissions/revoke { permissionCodes }
      ├─ 再 GET /admin/users/{id}/permissions 回读，用后端结果覆盖勾选态（不信任本地）
      └─ 重新拉一次变更日志
```

设计要点（后端可据此判断前端是否重复调用）：保存是**增量 diff**，不做全量覆盖；`reason` 字段前端当前未采集，恒为 `undefined`。

## 4. 权限分组是前端本地聚合的

后端 `GET /admin/permissions` 返回的是扁平数组（`code` / `name` / `module` / `action` / `description`）。前端按 `module` 在本机聚合成两栏分组，中文名取 `constants/enums.ts` 的 `PERMISSION_MODULE_LABEL`（24 项）：

`resident`→住户管理、`merchant`→商家管理、`reports/report`→报表数据、`announcements/announcement`→通告管理、`point_pool`→积分池、`points`→积分管理、`coordinator`→统筹管理、`delivery`→配送管理、`property_company`→物业公司、`permission`→权限管理、`activity`→活动管理、`notice`→通知收集、`refund`→退款审批、`coin`→物业币、`settlement`→结算管理、`withdrawal`→提现管理、`forum`→社区论坛、`community`→社区管理、`price_approval`→价格审批、`canteen`→社区食堂、`order`→订单管理、`finance`→财务管理、`platform`→平台配置、`navigation`→导航配置、`role`→角色账号、`operator`→操作员。

未识别的 `module` 落到"其他"。**这层分组纯属展示**，不参与任何准入判断——请注意它与"页面"没有对应关系。

## 5. 登录后前端手上究竟有什么（断点所在）

登录流程（`stores/auth.ts:255-307`）：

```
POST /auth/admin-login  → 取 data.resident 存入 profile（localStorage）
  └─ 若角色允许调 /auth/profile（canUseProfileApi）→ 再请求一次并覆盖
       propertySubRole 取值优先级：/auth/profile → admin-login 响应 → JWT claim
```

`profile` 里落地的字段：`id`、`name`、`phone`、`role`、`propertySubRole`、`propertyCompanyId`，以及 `isBuildingLeader`、`isPropertyManager`、`isCoordinator`、`isSectorLeader`、`isIndividualLeader`、`isActivityLeader`、`isResidentMerchant`、`isDistributor` 等布尔标签。

**没有 `effectivePermissions`，也没有任何权限码字段。** `/auth/profile` 的响应（文档 §1.6）本身也不返回。

这就是消费端的断点：前端不是"没写过滤逻辑"，而是**登录后没有任何权限码可用来过滤**。

## 6. 准入三层，权限码零参与

| 层 | 实现 | 判定依据 |
| --- | --- | --- |
| ① 路由 | `router/index.ts` `beforeEach` → `canAccessRouteAny` | `role` + 标签派生角色（楼长/统筹/板块/个体/组长） |
| ② 路由二次 | 同守卫 → `canAccessLeaderOnlyRoute` | `propertySubRole`（14 个路由硬编码在 `PROPERTY_LEADER_ONLY_ROUTES`） |
| ③ 菜单 | `constants/roles.ts` `getMenusForProfile` | 静态表 `ROLE_MENUS` / `propertyOperatorMenus` / 领导菜单动态插入 |
| ④ 按钮 | — | **无**（无 `hasPermission`、无 `v-permission`，页面内按钮不看权限） |

14 个领导专属路由（`menus.ts:85-100`，硬编码）：

`param`、`permission`、`property-operators`、`company-account`、`settlement-account`、`regional-leaders`、`price-approvals`、`coordinators`、`reward-grant-approvals`、`property-bank-cards`、`region-quotas`、`navigation-items`、`activity-group-reviews`、`settlement-config`

界面层的现状还需说明一点：**没有统一的 403 页面**。`request.ts` 的 `onForbidden` 是空实现（注释"403 仅提示"），接口 403 只由各页面自己 catch 显示文案。将来接权限码时这一块需要新建。

## 7. 为什么"给角色配了参数配置，登录看不到参数配置"

以你测的场景逐步还原（每一步都可对照代码核对）：

1. 在「物业操作员」页创建账号时，表单里有一个**自由文本**的"权限预设编码（可选）"输入框（`PropertyOperators.vue:93-95`），提交时原样透传为 `permissionPresetCode`。前端不解析它、不做下拉、不校验是否存在——它只是一串字符。
2. 该账号登录后：`role=property_admin`，`propertySubRole=property_operator`。
3. 菜单计算走 `getMenusForRole` 的这一支（`roles.ts:273-276`）：
   ```ts
   role === USER_ROLE.PROPERTY_ADMIN && !isPropertyLeader(identity)
     ? [...propertyOperatorMenus]   // ← 操作员走这里
     : [...adminMenus]
   ```
4. `propertyOperatorMenus = adminMenus.filter(m => !PROPERTY_LEADER_ONLY_ROUTES.includes(m.route))` → **`param`、`permission`、`property-operators` 等 14 项被整条剔除**，侧栏不会出现"参数配置"。
5. 即使手动在地址栏输入 `/param`：守卫第②层 `canAccessLeaderOnlyRoute` 返回 false → 静默重定向首页，用户只会觉得"打不开/被弹回"。
6. 所以预设编码里到底有没有参数配置对应的权限码，**前端一次都没读过**，现象必然一致。

另外一个容易踩的点（建议后端顺手核对账号数据）：代码注释明确写着"operator / subRole 为空走操作员菜单"（`roles.ts:272`）。也就是说**只要账号的 `propertySubRole` 是 `null` / 空串，即使 `role=property_admin`，也会按操作员渲染菜单**，同样没有参数配置。请后端确认测试账号在库里 `property_sub_role` 的实际落值，以及 `/auth/admin-login` 与 `/auth/profile` 是否都稳定返回该字段——这一项如果为空，前端所有领导入口都会消失，与权限配置无关。

## 10. 请后端确认的四点（与配套文档一致）

1. 权限码取数口：新增 `GET /auth/my-permissions`，或 `/auth/profile` 增加 `effectivePermissions`（需为最终生效集合）。
2. 权限码 ↔ 页面/模块对照表：现有 `resident:read` 这类资源级编码无法映射到 60+ 个菜单项，请给全量映射或明确按 `module` 粗粒度。
