# 权限配置配了不生效：缺权限码取数口与页面映射

> **状态**：待后端（需契约确认，前端无法单方面补齐）
> **日期**：2026-10-28
> **入口**：管理端 → 系统管理 → 权限配置（`/permission`）
> **相关接口**：§48.2 `GET /admin/permissions`、§48.3–48.5 `/admin/role-presets`、§48.6 `GET /admin/users/{id}/permissions`、§48.7–48.8 `grant` / `revoke`、§48.9 `permission-change-logs`、§1.6 `GET /auth/profile`

## 现象

在权限配置页给某账号（或套用角色预设）勾选/取消权限，保存成功、变更日志有记录。但用该账号重新登录后，**左侧菜单、可访问页面、页面内按钮全部没有变化**，无法判断权限到底有没有生效。

具体复现：给一个 `property_operator` 账号勾上"参数配置"相关权限 → 保存 → 用该账号登录 → 左侧仍然没有「参数配置」入口。

## 归因

不是配置没写进库，而是**前端从来没有读取过权限码**。配置链路（写）是通的，消费链路（读）为 0。

前端已核对的代码事实：

| 环节 | 现状 |
| --- | --- |
| 配置端接口接入 | 完整：权限池、角色预设（只读）、账号列表、用户权限详情、grant/revoke、变更日志 |
| `GET /auth/profile` 返回权限码 | **不返回**，`data` 中无 `effectivePermissions` / `permissions` 字段 |
| 前端登录态存储 | `auth.profile` 无权限字段，登录后手上没有任何权限码 |
| 菜单生成 | 静态表按 `role` / `propertySubRole` 分组，不含权限码（`constants/menus.ts`、`constants/roles.ts` 的 `getMenusForProfile`） |
| 路由守卫 | 只判 `role`；「参数配置 / 权限配置 / 操作员管理」硬编码在 `PROPERTY_LEADER_ONLY_ROUTES`，只认 `propertySubRole=property_leader`（`router/index.ts`、`roles.ts` 的 `canAccessRoute` / `canAccessLeaderOnlyRoute`） |
| 按钮级控制 | 无 `hasPermission` / `v-permission` |

结论：只要权限码不进前端，权限配置在产品表现上必然是"配了没反应"。当前唯一会真生效的地方是后端接口级鉴权——表现为接口 403 / `20004`、页面报错，而不是菜单变化。

## 需要后端给出的 4 件事

### 1. 权限码取数口（优先级最高）

现状：`/auth/profile` 不含权限码；§48.6 `GET /admin/users/{id}/permissions` 的 Roles 只有 `platform_admin`、`property_admin`，`resident` / `merchant` / `courier` 等角色查不了自己。

请在以下两种中选一种实现：

- **A（推荐）**：新增 `GET /auth/my-permissions`，登录即可调用，返回

```json
{
  "code": 0,
  "data": {
    "role": "property_admin",
    "propertySubRole": "property_operator",
    "rolePresetId": "rp_demo001",
    "rolePresetName": "物业管理员",
    "effectivePermissions": ["resident:read", "merchant:read", "reports:view"]
  }
}
```

  `effectivePermissions` 需为**最终生效集合**（角色预设 ∪ 额外授予 − 显式撤销），与 §48.6 同口径。

- **B**：在 §1.6 `/auth/profile` 响应中增加 `effectivePermissions: string[]`（字段同 A），前端首屏即可拿到，无需二次请求。

对应前端改造（拿到 A 或 B 之后）：登录 → 写入 auth store → 路由守卫在 `role` 通过后再判权限码 → 菜单按同一映射过滤 → 无权限落 403 页。这部分前端自己做，不需要后端配合。

### 2. 权限码 ↔ 页面/模块 对照表

这是真正的阻断点。当前权限码是**资源级**（`resident:read`、`merchant:audit`），而管理端有 100 多个路由，两者没有对应关系，前端无法把 `resident:read` 映射到「业主管理」菜单。

请二选一提供：

- **方案 1（精确）**：一份 `route name → permission code` 对照表（或页面级权限码，如 `page:param-config`），前端直接按表过滤；
- **方案 2（粗粒度，落地更快）**：以 §48.2 已有的 `module` 字段为准，提供权威清单（每项含 `code` / `module` / `action` / `name`），并明确"访问某模块页面需要哪个 action"（如 `module:read` 即可见菜单）。前端按 `module → 菜单分组` 建一张本地映射表。

任一方案都需要**一次性给全量**，否则漏掉的权限码会导致页面永久不可见。

### 3. 统一权限码格式

文档内目前并存两种写法，前端无法同时匹配：

| 出现位置 | 写法 |
| --- | --- |
| §48.2 权限列表、§48.6 `effectivePermissions` | `resident:read`、`merchant:audit` |
| §48.5 更新角色预设的请求示例 | `permission.resident.read`、`permission.merchant.read` |

请确认唯一口径（建议 `resource:action`），并说明旧格式是否需要别名兼容；`GET /admin/permissions` 返回的 `code` 即为准。

### 4. 明确谁有权 grant / revoke

§48.7 / §48.8 的 Roles 只有 `platform_admin`，但权限配置页对 `property_admin`（含 `property_leader`）是开放的：

- 路由 meta：`roles: [...ADMIN_ROLES], propertyLeaderOnly: true`；
- 结果：物业管理员能进页面、能勾选、点保存会拿到 403 `20004`，看起来像"保存失败/配置没生效"。

请择一处理：

- 若物业管理员**可以**操作权限：更新 §48.7 / §48.8 的 Roles，或改为"持有 `permission.manage` 的账号"；
- 若**不可以**：请回复确认，前端将权限配置页收窄为平台管理员可见，并去掉误导性的保存按钮。

2. 路由守卫增加权限码判定，无权限跳 403 页；

5. 按钮级 `hasPermission`。

## 验收标准（前端与后端可共同执行）

1. 平台管理员在权限配置页撤销账号 A 的「报表」相关权限 → 保存 → 日志出现 `revoke` 记录；
2. 账号 A 重新登录 → `GET /auth/my-permissions`（或 `/auth/profile`）返回的 `effectivePermissions` 中不含该码；
3. 账号 A 左侧菜单中对应入口消失；直接输入路由地址访问 → 落到 403 页而非空白；
4. 账号 A 调用对应接口 → 后端返回 403 / `20004`（这条现在就已生效，可先行验证）。

第 2 步不通，第 3 步前端无法做；第 2 步通了但第 2 项（映射表）缺失，菜单过滤只能按模块粗粒度近似，会出现"勾了某权限但菜单不动"或"没勾也可见"的偏差。
