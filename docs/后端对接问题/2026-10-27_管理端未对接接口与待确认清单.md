## 三、需要后端确认口径（8 条，每条都卡着前端一个实现选择）

### 3.1 §103.1 保存权限：前端靠什么字段判断「我是平台管理员」

文档要求非 `platform_admin` 把结算配置、订单配置的保存按钮置灰。前端目前 `SettlementConfig.vue` 和 `Param.vue:682` 都没有判断，因为不确定用哪个字段最可靠。

**请确认**：`/auth/profile` 返回的 `role === 'platform_admin'` 是否是唯一判据？是否还有「平台管理员但被限定某物业」的细分情况（若有，置灰逻辑要跟着变）。

同类还有 `GET/PUT /admin/platform-config`（附录 A.8 也写了「更新仅 platform_admin」）、`/admin/settlement-config`、`/admin/order-config` —— 请给一张这三组接口的读/写权限矩阵，前端一次性按矩阵做置灰。

### 3.2 §102.4 角色修改 vs §2.8 编辑权限，两条规则怎么并存

- §102.4（v8.16）：`role` 只有 `platform_admin` 能改，`property_admin` 改返回 20004。
- 前端既有实现（`Resident.vue:705` 注释按「§2.8」口径）：只有 `property_admin` 可编辑他人信息，"platform_admin 无此权限"。

那么 **platform_admin 想改某人 role，走哪个接口**？前端住户编辑弹窗是整对象提交（含 `role` 字段），如果 platform_admin 调 `PUT /residents/{id}` 会因「无编辑权限」被拒，就没法改角色 —— 两条规则互斥。

**请明确**：是否需要单独的 `PUT /admin/residents/{id}/role`？还是 platform_admin 对 `PUT /residents/{id}` 已放行、只校验 `role` 字段？

### 3.3 §103.3 初始密码：`initialPassword` 是否保证 100% 返回

前端 `PropertyCompanies.vue:272` 的写法是：

```js
const pwd = created.adminAccount?.initialPassword || 'admin123456'
```

`'admin123456'` 正是 §103.3 说「登录直接返回 403 初始密码已禁用」的那个旧密码。**如果某次创建响应没带 `initialPassword`，弹窗会展示一个必然登录失败的密码**，管理员照着念给客户，客户登不上。

**请确认**：
1. `POST /admin/property-companies`（含新增物业管理员）是否**每种分支**都返回 `initialPassword`？
2. 若不保证，请给「如何补救」的接口（重置密码的路径是什么？文档里没找到）。

### 3.4 §102.5 提现错误码：94006 前端怎么区分

前端错误码表里有 `94005`（提现已被冻结），**没有 94006**（可提现余额不足，v8.16 新增）。

**请确认**：94006 是走统一 `message` 透出，还是前端要专门做「刷新余额 + 高亮可提现上限」的联动？如果需要联动，请确认 94006 响应体里是否带 `withdrawableAmount` 当前值（不带的话前端得再发一次 `GET /merchants/my`）。

另外 `POST /admin/merchant-withdrawals/{id}/audit` 在 `pending → approved` 时会**再次校验可提现余额**，此时余额不足返回的是 94006 还是别的码？审核端要给出「余额已变化，请重新核对」的提示，需要知道码值。

### 3.5 配送双状态：管理端报表按哪个口径算 GMV

这是从 10-22 就挂着的问题，现在仍未定，前端 `mappers.ts:838-852` 只能把 `delivered` 与 `completed` 当同类展示，并加了注释冻结改动。

- 本仓历史口径：`delivered` = 物流终态，`completed` = 历史脏数据
- v8.12 移动端文档口径：`delivered` = 已送达待居民确认（中间态），`completed` = 物流终态

**请明确**：`GET /admin/dashboard/overview` 的 GMV / 结算金额，是按 `orders.status=completed` 统计，还是按 `delivery.status` 统计？两者在「配送员已点送达、居民还没确认收货」的窗口里数值不同，管理端报表和商家看到的钱会对不上。

同理请确认 `GET /admin/delivery-orders` 列表返回的 `deliveryStatus` 实际取值域（是否还会出现 `delivered`）。

### 3.6 业主小店审核列表：5 个店铺资料字段是否返回

`resident_merchants` 新增了 `shopName / description / businessHours / contactPhone / coverUrl`（§5.1）。管理端审核页 `ResidentMerchants.vue` 现在是「申请人 / 小区 / 保证金 / 状态 / 对外展示 / 申请时间」，**看不到店名和封面**，审核没法判断这店是卖什么的。

**请确认**：`GET /admin/resident-merchant-applications` 和 `GET /admin/resident-merchants`（列表）是否会返回这 5 个字段？不返回的话前端加了列也只能显示「—」。

### 3.7 负责人身份：「标签 true + status=active」双条件，列表要不要返回 status

文档 §1.2 要求权限判断改成「标签为 true **且** 业务表 status=active」双条件，被停用时 UI 要显示「已停用」。

**请确认**：`GET /admin/residents`（列表）和 `GET /admin/residents/{id}`（详情）是否会返回各身份的 `status`？现在详情只返回布尔标签（`isCoordinator` 等），无法区分「在职」和「已停用但标签还为 true」。

若后端保证「停用即标签置 false」，那前端就不用做双条件了 —— 请给一句明确结论，这决定前端要不要加这一层。

### 3.8 分成变更单审批归属（挂着最久的一条）

个体负责人在移动端改商家分成比例 → 后端生成 `PriceApproval` 待审。文档 §3.2 说由**板块负责人**审批，但管理端现状是**物业领导**审批（`roles.ts:159-163` `canAuditPriceApproval` 只放行 `property_leader`，平台管理员都不可审）。

**请产品+后端给一句**：这类单据到底进谁的待办？如果确实归板块负责人，那 PC 端要新增板块负责人审批入口；如果归物业领导，文档 §3.2 需要改。**不定这一条，个体负责人改分成后会一直挂单。**
