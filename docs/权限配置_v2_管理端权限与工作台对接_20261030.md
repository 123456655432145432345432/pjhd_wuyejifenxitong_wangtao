## 0. 一句话结论

v2 的核心变化是「菜单/路由/按钮只看 `effectivePermissions`，身份只看 `roleCodes` + `adminWorkspace`」。
前端已按这个口径改完：**能给标签身份（活动组长 / 统筹 / 板块 / 个体 / 社区管理员）授予的管理端入口，
现在会真的出现在对方侧栏里，撤权后消失**；权限配置页也补上了 `adminOnly`、标签身份展示、
可授权限收敛、内置预设锁定、变更原因。

但有两处**不是前端能解决的**，见 §6：44 个权限码里仍有 5 个在本仓没有对应页面；
`directed_message:*` 与 `points` 等 5 条路由因为与标签工作台共用而被刻意排除在门控之外。

## 1. 判定顺序（四层，这是全部行为的来源）

```
① 是否登录            → 否：/login
② meta.roles 命中？    → 命中：进 ③
                       → 不命中：走「权限码放行通道」（见下），仍不通过则弹回本角色落地页
③ propertyLeaderOnly？ → 未通过且不是走通道进来的：弹回落地页
④ 路由登记了权限码？    → 是：adminWorkspace 明确 false → /403（admin_workspace）
                         hasPermission(code) 为假 → /403（显示缺失的码）
```

**权限码放行通道**（v2 新增，解决"标签身份 role=resident 被 role 拦死"）必须同时满足四条：

| 条件 | 原因 |
|---|---|
| 该路由已在 `ROUTE_PERMISSION` 登记 | 未登记路由不因这条通道扩大可达范围 |
| 身份是 `platform_admin` / `property_admin` / `community_admin` / `role=resident` | 商家 / 配送员 / 技工**排除**，否则持 `delivery:grab` 的快递员会进到管理端「送货管理」 |
| `adminWorkspace !== false` | 普通住户（明确 false）一律不进 |
| `hasPermissionStrict(code)` 命中 | 严格模式：权限未加载 → 拒绝（不走 fail-open） |

`hasPermission`（菜单/按钮用）与 `hasPermissionStrict`（跨工作台通行用）的差别只有两点：
前者在"权限未加载"时放行（宁可多显示、由后端兜底），后者拒绝（宁可少放行、防越权）。

## 3. 菜单：过滤 + 追加

只靠"过滤"无法让标签身份出现新 tab（它们的角色菜单里本来就没有管理端项），所以是两层：

1. `filterMenusByPermission()` —— 登记的码未命中就移除；
2. `appendMenusByPermission()` —— 命中 `PERMISSION_MENU_CATALOG` 就把入口追加到菜单末尾（27 条目录，按码索引，同路由不重复）。

追加只对「管理端 / 领导标签身份」生效（`platform_admin` / `property_admin` / `community_admin` / `role=resident`），
商家 / 配送员 / 技工工作台不参与 —— 否则会给快递员凭空加出「送货管理」。

同时补了 `community_admin` 的完整支持：专属菜单（仅「社区论坛」）、落地页 `community-forum`、
侧栏副标题「社区管理台」。它不再落到 `dashboard`，避免默认没有 `data:view` 时登录即 403。

| §5.3 按身份收敛可授权限 | 标签身份只列 `grantableToTagIdentities=true`；物业端隐藏 `isPlatformOnly`；平台管理员全量 |

## 6. 前端仍未覆盖的部分（需要后端 / 产品决策）

### 6.1 五个权限码在本仓没有对应页面

`log:read`（操作日志）、`coin:freeze`（物业币冻结）、`point:clear_run`（2 年积分清零）、
`notice:collect`（通知征集）、`merchant:read/create/update`（平台商家库）、`promotion:push` 的优惠券页、
`consultation:manage`（咨询管理：`views/admin/Consultants.vue` 已存在但未挂路由、无菜单）。

→ 这些码在权限池里可以授予，但前端没有页面可显示，授了也不会有 tab。
**需要产品确认是先做页面还是先隐藏这些勾选项。**

### 6.2 六条路由刻意不接权限码（见 §2 表）

影响：统筹/活动组长等身份在这些页面上的可见性仍由角色决定，不由权限码决定。
如果后端希望"撤掉 `directed_message:read` 后统筹的定向推送 tab 消失"，需要先拆路由
（把管理端与工作台的定向消息拆成两个页面），否则只能二选一。

### 6.3 物业币显示开关的落点

已落地在「参数配置 → 物业币」区块（领导专属页面，`property_admin` / `platform_admin` 可达），
因为「物业公司」页是 `platform_admin` 专属，放那里物业侧用不了。
开关按 `coin:display_control` 渲染；后端对该权限码属于「可授标签」，标签身份若被授予该码，
需能进入「参数配置」页才看得到开关 —— 而参数配置是 `propertyLeaderOnly`，两者冲突。
**这点请后端确认：`coin:display_control` 到底给谁用。** 若确认只给物业主账号，现状即可；若要给标签身份，
需要把该开关单独挪到一个不受 `propertyLeaderOnly` 约束的页面。

### 6.4 状态字段缺失时的兜底

`adminWorkspace` 未下发（老环境）时按"放行"处理，避免升级瞬间全员 403。
这意味着：**后端必须尽快下发该字段**，否则历史持有 `community:read` 的普通住户仍可混进社区论坛。

`roleCodes` 未下发时，前端用 `isActivityLeader` / `isCoordinator` 等布尔字段派生，不影响主链路。

## 8. 风险与开关

- **总开关**：`PERMISSION_GUARD_ENABLED = false` 可整体退回纯角色控制（一行，无需改其它代码）。
- **唯一的自锁风险**：领导的预设必须含 `permission:read` / `config:set`，否则领导看不到「权限配置」「参数配置」。
  已有兜底：`property_admin` 在 `hasPermission` / `hasPermissionStrict` 中全量放行，不会把自己锁在门外。
- **社区管理员兜底**：`community_admin` 对 `community:*` 恒定放行（文档 §4 写明默认持有），
  即使后端预设未下发也不会登录即 403。
- **登录后刷新权限**：切换角色、保存权限、刷新页面各拉一次 `GET /auth/my-permissions`；
  被授权方需重新登录或刷新才生效（后端不改 token 内的权限快照）。
