# 管理端「参数配置」落库实现核对（2026-10-30）

> 结论先说：**核心业务参数（分成、门槛、订单、提现）是真落库的；
> 但「功能开关 / 商城抵扣 / 积分兑换比 / 按重量加价 / 积分分成直改」这批字段
> 原先被提交到了一个不含这些字段的 DTO 上，后端按「仅更新非 null 字段」处理时会被静默忽略。**
> 本轮已把可前端自决的部分改完，其余需后端确认。

核对范围：`src/views/Param.vue`（1899 行）+ 其调用的 8 个接口，对照
`docs/API接口文档_v8.25_下载副本.md` §51.4 / §51.6 / §51.8 / §69 / §79 / §80 / §14.6。

---

## 1. 判定依据：管理端更新接口的字段全集

§51.4 明确：`PUT /admin/property-companies/{id}`、`PATCH /{id}/status`、
`PATCH /{id}/config` **共用同一个 DTO** `UpdatePropertyCompanyRequest`，字段全集为 22 项：

```
name, logoUrl, contactPhone, address, status,
platformShareRate, propertyShareRate, coordinatorShareRate,
sectorLeaderRate, individualLeaderRate,
coinDisplayEnabled, coinIssueMode, coinExpiryDays, coinFreezeDefault,
deliveryBaseFee, deliveryCourierShareRate, deliveryCourierPerOrder,
withdrawalFeeRate, pointToFeeRate, twoYearClearEnabled,
pointTransferEnabled, pointTransferMinYears, neighborDailyContactLimit
```

并且文档有一句关键提示（原文）：

> 请求体**没有** `residentPointShareRate` / `merchantPointShareRate` / `coinPointShareRate` /
> `sharedPointShareRate`，传入会被忽略；分成调整请使用上表字段或走 §65 价格审批。

前端 `mapFormToConfig()` 提交的字段里，**12 项不在上述全集内**：

```
pointEnabled, pointDisplayEnabled, coinEnabled,
coinMallEnabled, coinMallMaxRatio, coinMallMinAmount,
deliveryPerKgFee, pointExchangeRate,
pointsAttributionMode, rewardAttributionMode,
regionalLeaderRate, projectLeaderRate
```

这 12 项就是「界面上能改、保存提示成功、刷新后回到原值」的来源。

## 4. 现在怎么验（5 分钟，逐条看「保存后刷新还在不在」）

用**平台管理员**登录 → 参数配置 → 选一家物业：

1. **关掉「启用积分功能」** → 保存 → 刷新页面。仍是关闭 = 落库；跳回开启 = 未落库，页面顶部会点名「启用积分功能」。
2. **「按重量加价」改成 0.35** → 保存 → 刷新。仍是 0.35 = 落库。
3. **「积分兑换比例」改成 120** → 保存 → 刷新。仍是 120 = 落库。
4. **积分分成四项**改成 40/30/20/10 → 保存 → 刷新。四项保留 = §14.6 路径可用。
5. **「向住户显示物业币入口」关掉** → 直接点「保存全局设置」→ 刷新。仍关闭 = 覆盖问题已解；被打回开启 = 后端仍按 `coinEnabled` 回写。
6. **商城抵扣三项**改数 → 保存 → 刷新。保留 = §69.2 对平台已放开。

用**物业领导**登录时，1/3/4 走的是：功能开关无写通道（会在回显校验里点名）、
积分分成走价格审批（提交后到「价格审批」页应看到 `resident_share_rate` 记录）。

浏览器 F12 → Network 里可看到本轮新增的两类请求：
`PUT /property-companies/{id}`（§14.6）与 `PUT /admin/coin-withdrawals/settings?propertyCompanyId=pc_xxx`。

## 5. 需后端确认（4 项，都影响这 6 个 ⚠️）

1. **§14.6 `PUT /property-companies/{id}` 是否仍对 `platform_admin` 开放？**
   `UpdatePropertyCompanyRequest` 是否与 §14.6 是同一 DTO？
   若已合并，建议直接把这 8 个字段补进 admin DTO，前端就不用分两条路径。
2. **`pointEnabled` / `coinEnabled` 是否有意只允许平台改？**
   物业领导在界面上能点这两个开关，但没有任何写入通道。若是设计如此，前端把开关置灰，
   否则每次保存都会出现「未落库」提示。
3. **§69.2 `mall-rules` 是否对 `platform_admin` 放开？**
   现状：平台管理员在三档商城抵扣上无写入通道（物业侧有）。
4. **`pointsAttributionMode`（积分归属）后端是否存在？**
   全文档 0 处出现；而 `rewardAttributionMode` 属 `/admin/platform-config`。
   前端已把这两项从参数配置页移除。

## 6. 仍然存在的结构性限制（非缺陷，记录）

- **订单配置是平台级全局参数**，不区分物业公司。页面顶部可切换物业，但切换后
  「核实时限 / 冻结期 / 退款窗口」不会变——这是 §51.8a 的口径，不是 bug。
- **分数三档校验只在携带任一三档字段时触发**（§51.6）。若 `platform-share-rates`
  读取失败、`platformSharePercent` 兜底为 0，保存时提交 0 + 物业 + 管理盘 ≠ 100 → 97006。
  已由「三档合计须约 100%」前置校验拦住，不会写坏数据，但会表现为「没改也保存失败」。
- **参考比例（区域 / 项目负责人）不参与主分成链**，仅作展示参照，改与不改不影响结算。
