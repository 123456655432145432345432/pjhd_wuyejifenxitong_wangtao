# 前端未完成 / 半实现项 — 前后端责任拆分

> **整理日期**：2026-08-03  
> **范围**：管理端与各角色门户中较实质的缺口（约 7 类）  
> **原则**：契约已具备 → 前端可直接做；缺字段 / 缺接口 / 方案未定 → 后端确认（或先产品拍板）  
> **说明**：不含 input placeholder、支付方式枚举 `mock`、空态「无图」等 UI 占位。README「全是 Mock」已过时，主体已接真实 API。

---

## 总览

| 缺口 | 前端直接做 | 后端确认 / 补接口 | 还要产品拍板 |
|------|------------|-------------------|--------------|
| 家庭 / 个人积分分栏 | 有字段后改 UI | 字段名与含义 | — |
| 服务聊天发价 | 仅当契约就绪 | 聊天报价契约或确认保留表单 | 表单 vs 聊天 |
| 统筹 / 板块 / 区域提现 | 有 API 后抄现成页 | 提现 API + 角色权限 | 区域是否独立账号 |
| 区域工作台 / 板块加区域 | 板块挂 CRUD（若权限允许） | 权限、独立角色、门户 API | 要不要独立工作台 |
| 账期起止 + 楼层排序 | 有字段后展示 / 加 floor 排序 | `feeStart/End`、`sort`+`floor`、跨页排序 | — |
| 技工对齐商家 | 默认不做；或复用商家页 | 主体 / API 是否共用 | 要不要全套能力 |
| 提现审批看板 | **可直接做**（列表聚合或抄汇总卡） | 可选：全库 summary | — |

**建议排期**：前端先做「提现审批看板」；并行让后端确认「积分双栏字段、提现 API、账期字段、询价方案」四块。

## 1. 家庭 / 个人积分分栏

### 现状

- `Points.vue` 住户详情只展示单一 `pointBalance`。
- 「建设积分」已有独立页 `CommunityPoints.vue`。
- 需求中的「家庭积分 / 个人积分」两栏未做。
- 前端 `types` 中尚无 `familyPointBalance` 等字段（部分文档曾写后端已有，本仓类型未对齐）。

### 前端可直接做

- 字段契约对齐后：积分页拆「家庭 / 个人」两列或两卡；详情弹窗同步展示。
- 建设积分继续走现有页，避免与个人/家庭余额混在一个数字里。

### 后端要确认

- 列表 / 详情是否返回家庭积分、个人积分（字段名、是否含成员汇总）。
- 与现有 `pointBalance` 的关系：是否废弃旧字段，还是 `pointBalance` 等于其中之一。

### 结论

UI 前端能做，但**必须先有后端字段契约**，否则只能做空壳。

---

## 2. 服务询价：仍走表单，非聊天发价

### 现状

- `MerchantServiceRequests.vue`：接单 / 跳过 / **弹窗报价**（金额、币种、说明、有效小时）→ `POST .../quote`。
- 物业侧有住户聊天 `property-chat`，但**未接到服务询价流**。
- 会话类型中虽有与 `service_request` 相关的枚举，管理端没有「在会话里发价 / 订单链接」页面。

### 前端可直接做

- 若产品认定「表单即正式方案」：保留现状，补文案说明即可。
- 若确定走聊天：可复用聊天 UI 壳，但发价按钮 / 报价卡片依赖新契约。

### 后端要确认

- **二选一**：
  1. 表单报价为正式方案，长期保留；
  2. 聊天内发价 —— 需消息体报价结构、订单链接、状态回写约定。
- 报价后住户端如何确认、是否生成订单；旧 `/quote` 是否废弃。

### 结论

改聊天链路**不能前端独做**；产品 / 后端不定方案，前端只能维持表单。

## 3. 统筹 / 板块 / 区域提现门户缺失

### 现状

- **已有提现**：商家、配送员、个体负责人、活动组长、技工。
- 统筹菜单无「提现」；板块仅有工作台 / 商家 / 排名 / 特惠。
- 区域只在物业端 `RegionalLeaders.vue` 做 CRUD，**无登录门户、无提现页**。
- `services.ts` 无统筹 / 板块 / 区域的 withdrawals API。

### 前端可直接做

- 有 API 后：仿 `IndividualLeaderWithdrawals.vue` / `MerchantWithdrawals.vue` 增加菜单、路由、申请 / 列表页。

### 后端要确认

- 是否提供如 `/coordinators/me/withdrawals`、板块 / 区域同类接口。
- 余额字段、手续费、审批流是否复用管理端提现审批。
- 区域负责人是否独立账号角色（当前无独立区域角色门户）。

### 结论

页面形态前端能抄现成提现页；**接口与角色权限必须后端先定**。

---

## 4. 区域 / 项目无独立工作台；板块端不能加区域

### 现状

- 物业领导：`RegionalLeaders.vue` 对区域 / 项目负责人 CRUD + 分成。
- 板块端 `sectorLeaderMenus` 只有 4 项，**没有「加区域」入口**。
- 无 `regional-leader-*` 路由 / 工作台（登录后不会进入区域专属壳）。

### 前端可直接做

- 若仅「板块代管区域」：板块菜单挂「区域负责人」列表，复用或收窄现有 CRUD（权限允许时）。
- 独立工作台：可仿统筹 / 板块做 overview + 菜单（需角色与 API 就绪）。

### 后端要确认

- 区域创建权限：板块能否调用现有 `/regional-leaders`，还是要板块专属接口。
- 区域 / 项目是否要独立登录角色、菜单范围、分成查看 / 提现。
- 项目负责人与区域负责人的关系、权限边界。

### 结论

「板块端加区域」在权限放开后前端可接；**独立工作台必须先有角色与 API，否则不要空做门户**。

## 5. 物业费账期起止 + 住户按楼层排序

### 现状 · 账期

- 住户列表 / 详情只有 `arrearsCount` / `arrearsAmount` 徽章。
- 欠费报表有 `period`、`dueDate`、`daysOverdue`，**没有**统一的「自 × 日起至 × 日到期」展示在住户主列表。
- `ResidentItem` 无 `feeStart` / `feeEnd`。

### 现状 · 排序

- 请求已带 `sort=+building,+unit,+room`，页内再用 `sortResidentsByAddress` 兜底。
- `floor` 在楼宇结构中有，**住户列表排序未使用 floor**。
- 跨页全局排序仍依赖后端是否真正按 `sort` 生效。

### 前端可直接做

- 有起止字段后：列表徽章 / 详情改为「自 A 至 B · 欠费 n 笔」。
- 若住户项带回 `floor`：前端 sort 可加上楼层；并提示「仅当前页排序」。
- 欠费报表已有 `dueDate`：可先在报表侧加强展示（不完全等于住户主列表需求）。

### 后端要确认

- 住户或欠费明细是否提供 `feeStart` / `feeEnd`（或 `periodStart` / `periodEnd`）。
- `GET /residents` 的 `sort` 是否真正支持 `building,unit,room`，是否增加 `floor`；空地址是否排最后。
- 跨页排序是否由服务端完成（前端分页兜底解决不了全局序）。

### 结论

展示改动前端能做；**字段与跨页排序是后端项**。

## 6. 技工未对齐完整商家能力（若产品要求）

### 现状

- 技工菜单：工作台、工单、服务、提现。
- 商家另有：商品、动态、关键词、广告、配送范围、积分等。
- 技工概览在 `/technicians/my` 失败时提示「待后端联调」，工单统计可能为 0。

### 前端可直接做

- **产品若确认「技工 ≠ 全套商家」**：保持现状，补说明文案即可。
- 产品若要求对齐：可挂载复用 `MerchantProducts` 等页（权限与 `merchantId` 映射要通）。
- 修好概览空态 / 错误提示（不依赖扩能力）。

### 后端要确认

- 技工账号能否走商家商品 / 广告 / 关键词 API，还是要技工专属路径。
- `/technicians/my`、工单接口稳定性；技工与商家主体是否同一 `merchantId`。

### 结论

扩能力前**先产品拍板**；拍板「要全套」后再前后端一起扩。默认前端不必先做。

---

## 7. 管理端提现审批仍是列表非看板

### 现状

- `MerchantWithdrawalApproval.vue`：搜索 + 状态 + 日期 + 表格审批。
- 商家端 `MerchantWithdrawals.vue` 已有汇总卡（可提现、审核中、已到账等）。
- 管理端审批页**没有**顶部统计卡。

### 前端可直接做

- 顶部增加「待审笔数 / 待审金额 / 今日已审 / 已通过金额」等，样式对齐商家提现页。
- 列表交互可保留，看板只是增强。
- 无专用汇总接口时，可对**当前筛选结果 / 已拉列表**做前端聚合，并标明统计范围。

### 后端要确认（可选）

- 是否有审批汇总接口。
- 若需要「全库汇总」而非当前筛选范围，需提供 `summary` 类接口。

### 结论

**少数可纯前端落地的体验项**；要全库准确汇总再向后端要 summary。
