## 1. 十二问逐条答复

### 1. 参数配置页目标角色

**答复：平台管理员 + 物业领导（仅本物业）。排除物业操作员。**

- 理由：参数直接决定本小区的积分/物业币/分账/提现行为，物业领导是业务责任人；操作员是执行岗，不应触碰涉及资金口径的参数。
- 前端当前状态：**页面层已满足**。`/param` 路由为 `roles = ADMIN_ROLES` + `propertyLeaderOnly: true`，`isPropertyLeader()` 只认 `platform_admin` 与 `property_sub_role = leader`，`property_operator` 直输 URL 也会被弹回落地页。菜单侧 `adminMenus` 同样已剔除该两项。
- 需要后端：把物业公司配置写接口的鉴权从 `property_company` 回退改为 **`config:set` + 本物业校验**，让 API 层与页面层口径一致（现在 operator 绕过页面直接调接口仍可写）。

### 2. `pointEnabled` / `coinEnabled` 写权限

**答复：平台 + 物业领导（仅本物业），不做平台独占。**

- 理由：这两个开关的语义是「本小区住户能否使用积分 / 物业币」。若平台独占，每开一个小区都要平台逐个操作，运营不可行；而它不涉及分成口径，风险等级低于分账比例。
- 必须同批交付（否则前端只能「看到入口、点了写失败」）：
  1. 详情 `GET /admin/property-companies/{id}` 返回这两个字段；
  2. 住户端 `GET /residents/me/points`、`GET /residents/me/coins` 返回对应开关，前端据此隐藏入口。
- 前端当前状态：`mapFormToConfig()` 已在提交这两个字段，后端补进 DTO 后**零改动即生效**。

### 3. 4 项积分分成

**答复：先下架。若将来保留平台直改，接受「仅平台 + 四项合计必须 100%」。**

- 理由：无任何消费方时，「能保存但不影响钱」的开关比不提供更危险——管理员会按它去解释分成结果，出问题后无从追查。
- 保留不动：**价格审批**里的积分分成提交/审批入口（那是审批流，不是参数页）。
- 前端当前状态：参数页「积分分成」整块（4 个百分比输入 + 平台直改/物业审批两条分支 + `mapPointShareToPayload`）待下架，规模约 60 行模板 + 2 个函数，改动可控。

### 4. 区域 / 项目负责人比例

**答复：下架，详情也不用补这两个字段。**

- 理由：没有对应角色、没有结算逻辑、详情也不返回。保留只会产生「改了没反应」的第三个字段。

### 5. 按重量加价（`deliveryPerKgFee`）

**答复：下架。属于新需求，需先有商品/订单重量体系。**

- 顺带请后端确认配送费的最终口径：**是否只有「商家 `deliveryFee` + `platformDeliveryShareRate` 抽成」这一条**。若是，前端会把该区块文案改成纯说明，不再提供「按重量加价」输入。

### 6. 物业级积分兑换比例（`pointExchangeRate`）

**答复：下架。不保留「纯展示」。**

- 若后端愿意在商家挂接配置页下发「物业默认值」，前端做**只读**展示并标注「继承自物业，修改请到商家配置」；否则整项删除。
- 不接受纯展示的原因同上：展示一个不参与计算的数字，等于制造误解。

### 7. 配送起步价（`deliveryBaseFee`）

**答复：保留，但明确为「平台商家利润测算参考」，不作为住户下单配送费。**

- 前端将把标签从「配送起步价」改为「利润测算参考值（不影响住户下单配送费）」，并归入平台商家相关区块。
- 若产品后续要求影响下单，按新需求立项，不在本次范围。

### 8. 物业币发放模式 / 新用户冻结

**答复：本期下架（按「预留」处理）。**

- 理由：`coinFreezeDefault` 写入后新住户 `coinFrozen` 恒为 `false`；`coinIssueMode` 无消费方。二者都没有可观察行为。
- 若后端倾向保留展示，请统一改为**灰显 + 标注「预留，暂不生效」**；前端默认按「下架」执行，以「有行为可验」为上线标准。

### 9. 订单配置

**答复：物业管理员只读。前端已实现，不需要改。**

- 现状：保存按钮 `:disabled="... || !canEditPlatformFinance"`，并显示「订单配置为平台级参数，可查看，仅 platform_admin 可以修改」。

### 10. 提现手续费率

**答复：仅平台。**（与后端建议「物业可改」不同，这是产品口径选择）

- 理由：费率直接影响住户到账金额，物业自定会造成同一平台内各小区到账不一致，客诉最终仍归平台；与「分账比例仅平台」保持同一治理口径。
- 前端现状：`withdrawalFeeRate` 位于 `canEditPlatformFinance` 分支内，非平台账号不发送且输入框置灰。
- 若产品改为物业可改：前端只需把该字段移出该分支（一处改动），但请后端先确认 `PATCH /{id}/config` 对该角色放行，否则会变成「能编辑、保存 403」。

### 11. 参数配置页权限码

**答复：统一 `config:set`。同意，并请后端一并收紧。**

- 前端已做：
  - `/param` 在 `ROUTE_PERMISSION` 中登记为 `config:set`，无码访问落 403 页并显示所需权限码；
  - 权限配置页对标签身份（活动组长 / 楼长 / 统筹等）**只开放 `community:*`**，`config:set` 不可授予；
  - 物业操作员默认套餐缺 `config:set`。
- 需要后端：
  1. 物业公司配置写接口改为 `config:set` 校验，去掉 `property_company` 回退；
  2. 明确 `property_operator` 是否保留该页 **GET** 读权限。若保留读、禁写，前端会把页面降级为只读并提示；若连读也禁，则与当前「操作员看不到该菜单」一致，前端不动。

### 12. 详情需要补哪些字段

**答复：只补 `pointEnabled` / `coinEnabled`（可写）。其余一律不补。**

- 理由：第 3/4/5/6 条已决定下架的字段，补进详情只会让前端「能回显一个不影响任何行为的数字」，是新的误导源。
- 若后端坚持保留只读回显，前端按「灰显 + 预留」呈现，不做保存校验。

## 2. 三条补充问题（后端清单里没有，但会卡住前端）

### A. `platformShareRate` 的写入通道没有闭环（优先级最高）

后端 §5.1 写的是「只读走 `GET /admin/platform-share-rates`；写入仅平台」，但前端当前是把 `platformShareRate` 放进 `PATCH /admin/property-companies/{id}/config` 的 payload 里提交（仅平台账号发送）。

请确认两者之一：

1. `PATCH /{id}/config` 确实接收 `platformShareRate` —— 那前端不改；
2. 不接收 —— 平台改「我们公司占比」必须走 `PUT /admin/platform-share-rates`，前端改调该接口。

**为什么必须先定**：一级三档（我们公司 + 物业 + 管理盘）必须合计 100%。如果平台占比写不进去，物业占比单独调就永远触发 97006，等于分账配置在平台侧无法完成。

### B. 错误码口径需要一张最终表

§4.1 给的是 `97020` / `97021`，§5.1 又提到原文档写的是 `40003` / `50006`。前端提示文案要按码分支，请给出最终码表，并确认语义是「本小区未启用该功能」（前端提示「本小区未启用积分功能，请联系平台」），而不是「参数非法」。

### C. 分账与手续费的可写角色与 §5.1 不一致

§5.1 把 `propertyShareRate`、`coordinatorShareRate`、`sectorLeaderRate`、`individualLeaderRate`、`withdrawalFeeRate` 标为「物业管理员可写」。按本答复第 1、10 条，我方口径是**全部仅平台**。请按此收紧，否则前端置灰、后端允许，会出现「绕过页面直接调接口改分成率」的缺口。

## 3. 本轮前端已改（1 处，纯缺陷修复）

**文件**：`src/views/Param.vue`

**改动**：删除 `handleSave()` 末尾的「回显校验」块。

被删掉的比对是 `pointExchangeRate`、`deliveryPerKgFee`、`pointEnabled`、`coinEnabled` 四项。后端 §3 已说明详情接口不返回这四个字段，`loadDetail()` 后本地值必然仍是旧值，于是**每次保存成功都会弹出红字「未落库」**。这是上一轮按错误前提加的代码，保留比删掉更糟。

**未改的部分**：`updateLegacy` 调用、积分分成区块、各项死字段的提交，全部保持原样等第 4 节阶段 A 统一处理。原因是后端 §8 明确要求「答复前前端先不要动结构」，且阶段 A 依赖后端 P0 是否把 `pointEnabled` / `coinEnabled` 补进 DTO——若先删掉提交，后端补完还得再加回来。

**校验**：`npx vue-tsc --noEmit` 与 `npm run build` 均通过（见交付消息）。
