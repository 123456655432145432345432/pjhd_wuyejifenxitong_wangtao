## 1. P0-①：`97020` / `97021` 撞码，请换段

### 1.1 冲突现状

后端《参数配置最终口径》§1.3 把 `97020` / `97021` 定为「本小区未启用积分 / 未启用物业币」。但前端这两张错误码表里，这两个数字码**已经是别的业务含义**：

| 码 | 前端现有文案 | 位置 |
| --- | --- | --- |
| `97020` | 订单已完成，不支持退款 | `src/api/request.ts` L58、`src/constants/enums.ts` L2526 |
| `97021` | 分账账户未就绪 | `src/api/request.ts` L59、`src/constants/enums.ts` L2527 |

如果按新口径覆盖，退款和分账的报错会显示成「本小区未启用积分功能」。所以前端**没有改这两个文案**，等后端定码。

### 1.2 更正：上一版建议的 `97040` / `97041` 不能用

我方在《参数配置_对后端12问答复_20261030》§2.B 建议改用 `97040` / `97041`，**这条建议无效**——`97040`–`97043` 已被一级代理（distributor）申请链路占用。核对后前端实际占用如下：

| 码段 | 用途 |
| --- | --- |
| `97001`–`97022`（中间有少量空号） | 催缴、分账比例、订单分账、退款、支付通道 |
| `97030`–`97033` | 个体负责人申请、物业公司删除 |
| `97040`–`97043` | 一级代理申请 |
| `97050`–`97051` | 社区论坛禁言 |

**请后端从 `97060` 起编号**（或任意 `97052` 以后未被占用的码），前端在 `request.ts` 与 `enums.ts` 两张表各补两行即可，改动 1 分钟。

### 1.3 顺带确认语义

## 2. P0-②：`adminWorkspace` 必须下发

### 2.1 前端当前逻辑（这是有意为之）

路由守卫第四层判断：

```
路由登记了权限码？
  → adminWorkspace 明确为 false → /403（admin_workspace）
  → hasPermission(code) 为假       → /403（显示缺失的码）
  → 否则放行
```

`canEnterAdminWorkspace()` 的实现是 `profile.adminWorkspace !== false`——**只有明确 `false` 才拦，`undefined` 视为放行**。

**原因**：升级瞬间老环境不下发该字段，如果按 `undefined → 拦` 处理，会导致所有管理端账号（含平台管理员）一次性 403，风险大于收益。

### 2.2 由此产生的缺口

普通住户如果历史上被授予过 `community:read`（v1 时期社区论坛只靠角色判断，存在脏数据），在 `adminWorkspace` 未下发的情况下：

- `roleCodes` 含 `resident` → 满足"管理端/标签身份"条件
- `adminWorkspace === undefined` → 放行
- `hasPermissionStrict('community:read')` → 命中
- **结果：普通住户能进 `/community-forum` 并看到管理端侧栏**

### 2.3 需要后端做

1. `GET /auth/profile` 与 `GET /auth/my-permissions` **都返回** `adminWorkspace`（布尔，非 null）；
2. 用一条 SQL 核对存量脏数据：`effectivePermissions` 里含 `community:read` 但实际是普通住户的账号有多少条。若数量可控，建议后端直接清掉这批脏授权。

拿到该字段后，前端**零改动即生效**（`stores/auth.ts` L131/L252 已按 undefined 兼容）。

## 4. P1-④：`coin:display_control` 的归属冲突

### 4.1 现状

「向住户显示物业币入口」开关落在 **参数配置 → 物业币** 区块，走独立接口 `PUT /admin/property-companies/{id}/coin-display`，按权限码 `coin:display_control` 渲染。

### 4.2 冲突

- `coin:display_control` 在 `GET /admin/permissions` 中被标为**可授标签身份**；
- 但参数配置页是 `propertyLeaderOnly`（仅 `platform_admin` / `property_sub_role = leader`），标签身份进不去。

**结论：标签身份即使被授予该码，也看不到这个开关。** 实际可用范围 = 物业主账号 + 平台。

### 4.3 需要后端定

| 选项 | 前端动作 |
| --- | --- |
| A. 该码只给物业主账号（把 `grantableToTagIdentities` 改为 false） | 不改，现状正确 |
| B. 要开放给标签身份 | 前端把开关单独挪到一个不受 `propertyLeaderOnly` 约束的页面（约 0.5 天） |

**建议 A**：物业币展示是租户级开关，交给物业主账号更符合治理口径。

## 5. P1-⑤：5 条共用路由无法按权限码控制

前端采用「声明式白名单」：只有登记在 `ROUTE_PERMISSION` 里的路由受权限码控制，未登记的一律维持角色逻辑。以下 5 条**刻意未登记**：

| 路由 | 未登记原因 |
| --- | --- |
| `directed-message` | 管理端与统筹/板块共用同一路由，登记后统筹缺码会丢掉自己工作台的「定向推送」 |
| `profile-rewards` / `transfer-to-property` | 与统筹/板块工作台共用 |
| `regional-leaders` | 与板块/个体工作台共用 |
| `points` | 一页同时含「查看 + 录入」，整页锁 `pool:read` 会误伤只查看的角色 |

**影响**：撤掉 `directed_message:read` 后，统筹的「定向推送」tab **不会消失**。

**可选方案**（需后端/产品确认走哪条）：

- **A. 接受现状**——这些页面继续由角色控制，权限码只管管理端专有页面。**当前默认**；
- **B. 拆路由**——把管理端与工作台的定向消息拆成两个页面（前端 1–2 天），拆完才能按码控制；
- **C. 页面内细化**——路由不锁，但页面内的写操作按 `v-permission` 控制（前端已具备该指令，`CommunityForum.vue` 在用）。
