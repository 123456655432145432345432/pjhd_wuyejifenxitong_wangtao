## 2. 三处需要后端确认（都不阻塞，但会影响验收判断）

### 2.1 ⚠️ `coin:display_control` 收紧后，物业领导的预设必须含该码

后端 §4 把 `coin.display_control` 收为物业领导专属，标签身份即使历史授权也不下发。前端参数配置页的「向住户显示物业币入口」开关渲染条件是：

```ts
const canEditCoinDisplay = computed(() => auth.hasPermission('coin:display_control'))
```

因此：**如果物业领导/主账号的默认预设里没有 `coin:display_control`，这个开关会直接不渲染**——不是权限问题，是有码才画。

请后端确认物业领导的预设（`isBuiltin` 那套）包含该码。若不含，需要补进预设，否则物业侧看不到这个开关。

### 2.2 权限码分隔符：请确认接口返回的是冒号

后端 §3 的 SQL 用点号（`p.code IN ('community.read', 'community.manage')`），§4 写 `coin.display_control`；而前端收到的 `GET /admin/permissions` 与 `effectivePermissions` 一直是冒号（`community:read`）。

前端文件头已按「数据库存点号、接口返回时转换」的口径实现，**代码里只认冒号**，没有任何点号兼容逻辑。目前验收通过说明接口确实返回冒号，所以判断 §3/§4 的点号只是 DB 列值。

但 `coin.display_control` 这次是新收紧的项，**请在实测时确认 `GET /admin/permissions` 返回的仍然是 `coin:display_control`**。若后端这次不小心透出了点号，参数页那个开关会静默消失，且 `grantableToTagIdentities=false` 也匹配不上。

### 2.3 小程序仓的错误码表不在本仓

本次只改了管理端（Vue3 仓）。`97070` / `97071` 的触发场景（住户在小程序里用积分/物业币被拒）发生在**小程序仓**（HBuilderX 项目），那边的错误码文案表需要单独同步，否则住户侧会看到裸码 `97070`。

若小程序端是后端直接返回 `message` 文案、不走本地码表，则无需处理——**请后端确认返回体里 `message` 是否已是中文**。
