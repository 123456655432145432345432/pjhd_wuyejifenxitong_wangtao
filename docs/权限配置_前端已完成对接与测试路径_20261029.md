## 1. 本次落地的核心变化

后端文档的关键结论是「管理端拆两层判断」，前端已按此重构：

| 层级 | 依据字段 | 前端落点 |
| --- | --- | --- |
| 能否进管理端 | `adminWorkspace` | `stores/auth.ts` → `canEnterAdminWorkspace()` + 路由守卫 |
| 进哪个工作台 | `roleCodes` / `isActivityLeader` | `getEffectiveRoles` 优先用后端 `roleCodes` |
| 工作台内有哪些 tab | `effectivePermissions` | `hasPermission()` + 菜单过滤/追加 |

### 判定规则（关键，防止误锁）

```
hasPermission(code):
  code 为空            → 放行
  platform_admin       → 放行
  权限未加载           → 放行（接口失败降级，不锁站）
  命中权限码           → 放行
  property_admin       → 放行（兜底：避免预设未配全把物业管理员锁死）
  其他（标签身份/住户）→ 拒绝
```

```
canEnterAdminWorkspace():
  profile.adminWorkspace === false  → 拒绝
  undefined（后端未下发）           → 放行
```

## 3. 郑美丽场景的完整链路

```
登录（admin-login）
  └→ GET /auth/profile
       role=resident, isActivityLeader=true, adminWorkspace=true,
       roleCodes=['activity_leader','resident'],
       effectivePermissions=['community:read','community:manage']
       └→ 前端落 permissions 缓存 + roleCodes + adminWorkspace
  └→ GET /auth/my-permissions（覆盖一次，保证实时）
落地页：getHomeRouteForProfile → activity_leader → activity-leader-overview（roles 含 activity_leader，通过）
侧栏：getMenusForProfile → activityLeaderMenus + residentMenus
      → filterMenusByPermission（无影响）
      → appendMenusByPermission：hasPermission('community:read')=true → 追加「社区论坛」
点「社区论坛」→ /community-forum
      → 角色门：roles=[platform_admin, property_admin, resident, community_admin] → resident 命中
      → 权限码门：community:read → 命中
      → 页面渲染
页面内：写按钮由 v-permission="community:manage" 控制
```

撤销后重新登录（或刷新页面）：
- `effectivePermissions` 不再含 `community:read` → 侧栏不再追加社区论坛
- 手输 `/community-forum` → `hasPermission('community:read')` = false → `/403?code=community:read`

## 4. 测试步骤

### 4.1 主链路（授 community:read + community:manage）

1. 平台管理员登录 → 权限配置 → 搜索「郑美丽」
2. 账号列表应显示标签「活动组组长」（若仍显示「住户」，说明后端未下发 `roleCodes`，见 §5）
3. 详情页应显示预设 `rp_003`，可授权限列表**只有社区论坛两项**
4. 勾选两项 → 保存
5. 用郑美丽登录 → 侧栏出现「社区论坛」→ 能看帖子列表
6. 删除/禁言按钮可见可点

### 4.2 只读场景（只授 community:read）

1. 撤掉 `community:manage`，只留 `community:read`
2. 郑美丽重新登录 → 侧栏仍有「社区论坛」，帖子/举报/禁言列表可看
3. 删帖、删评论、禁言、下发禁言按钮**全部不可见**（DOM 存在但 `display:none`）

### 4.3 撤销场景

1. 两项都撤掉 → 郑美丽重新登录
2. 侧栏「社区论坛」消失
3. 手输 `/community-forum` → 落到 403 页，提示缺少 `community:read`

### 4.4 反向验证（普通住户不该进来）

1. 用一个普通住户账号（无任何标签）登录
2. 手输 `/community-forum` → 应落 403
3. 若进了页面，说明后端未下发 `adminWorkspace=false`，需要后端补

## 5. 依赖后端的字段（缺失时的表现）

| 字段 | 缺失时前端表现 |
| --- | --- |
| `adminWorkspace` | 视为放行，普通住户若持有 `community:read` 会误入。**必须下发** |
| `roleCodes` | 回落到本地标签派生（`isActivityLeader` 等仍能识别活动组长）；权限配置页标签显示正常，但接口若只给 role 则显示「住户」 |
| `grantableToTagIdentities` | 若全部未下发，前端不过滤，标签身份会看到全部权限，勾错由后端 `10002` 拒绝兜底 |
| `effectivePermissions` | 必须在 `/auth/profile` 或 `/auth/my-permissions` 至少一处下发，否则门控降级为角色控制 |

## 6. 已知边界

1. **社区论坛数据范围按物业公司**，不按活动组。郑美丽能看到本物业公司全部帖子与举报。若要按活动组收敛需另立需求（文档 §3.3 已注明）。
2. **`adminWorkspace` 判断只作用于权限驱动型页面**（`ROUTE_PERMISSION` 登记过的路由），不做全局拦截。原因是当前 SPA 里住户、商家、配送员共用同一个 router，全局拦截会把非管理端角色锁在 403。
3. **未登记的 30 多个管理菜单仍按角色放行**，与文档 §8「其他菜单等后端接入后再切」一致。
4. 权限配置页目前不做「活动组长之外的其他标签身份」差异化，凡 `role=resident` 或 `community_admin` 一律按标签身份收敛，只会更严不会更松。
