## 1. 配送凭证上传 `category`：本仓一直用错值

### 1.1 现状

| 位置 | 当前值 | 说明 |
|---|---|---|
| `CourierTasks.vue:194` | `category="proof"` | 配送员送达凭证，`MediaUploader` 直传 `POST /files/upload` |
| `RoleWithdrawalApproval.vue:173` | `FILE_CATEGORY.PROOF`（= `'proof'`） | 管理端**提现转账凭证** |
| `constants/enums.ts:2240` | `FILE_CATEGORY` 无 `delivery_proof`，也无 `product` | 枚举与 v8.25 白名单已漂移 |

### 1.2 问题

v8.25 文档 §files/upload（第 6232 行）白名单是：

```
avatar / announcement / merchant / service / activity / product
```

**没有 `proof`**。且第 6234 行明确写「配送员上传配送凭证：使用 `category=service`」。

所以本仓这两处 `'proof'` 在 v8.26 之前属于非法值，正常应返回 `10002 category值无效`。v8.26 把 `proof` 加为 `delivery_proof` 的别名后，两处会**静默恢复可用**——但这是一个语义错位，而不是修好了。

### 1.3 必须处理：转账凭证会被归进配送凭证桶

v8.26 §1.2 规定 `delivery_proof` 不限累计、允许 mp4、单文件 10MB。而 `RoleWithdrawalApproval.vue` 传的 `proof` 归一后就是 `delivery_proof`，导致：

1. 财务人工转账凭证被计入「配送凭证」分类，按分类排查/清理时无法区分；
2. 这些凭证脱离原有上限保护（不限累计）；
3. 若后续要给「提现转账凭证」做单独保留策略，历史数据已混淆。

### 1.4 建议改法

- `CourierTasks.vue:194` → `category="delivery_proof"`（规范值，不再依赖别名）
- `FILE_CATEGORY` 补 `DELIVERY_PROOF: 'delivery_proof'`，同时补缺失的 `PRODUCT: 'product'`
- `RoleWithdrawalApproval.vue:173` → **等后端明确「提现转账凭证」该用哪个 category**
  - 候选 A：后端新增 `withdrawal_proof`（推荐，语义清晰、独立限额）
  - 候选 B：退回 `service`（但有「每个上传者累计最多 6 个文件」上限，管理员长期审核会撞墙）
  - 候选 C：继续用 `delivery_proof`（接受混淆）

> 顺带请后端确认：`proof` → `delivery_proof` 的别名归一，是否会对**已存在的** `category='proof'` 历史文件做回溯（查询时归一还是 `UPDATE`）？影响管理端按分类统计的口径。

## 2. 商家广告微信支付：本仓只有一半能做

### 2.1 现状与偏差

| 项 | v8.26 要求 | 前端现状 | 后果 |
|---|---|---|---|
| 支付方式取值 | 只保留 `free` + `wechat`，`coin/point/mock` 已下线，传了报 10002 | `MERCHANT_AD_PAYMENT_METHOD` 仍有 5 个值，支付单选框 5 个选项全展示 | 用户选到已下线方式必失败 |
| 表单默认值 | 应与可选项一致 | `MerchantAds.vue:230/240` 默认 `paymentMethod: COIN` | **新建广告默认就带非法值，不选就会 10002** |
| 微信入口显隐 | 由 `GET /merchant/ads/quote`、`/quota` 的 `wechatPaymentEnabled` 动态控制，**不要写死「暂未开放」** | 无该字段；改用 `merchantApplymentApi.getMine()` 的进件状态推断（`wechatPayAvailable`） | 进件已完成但通道未配置时，前端仍展示微信支付，点下去 10002 |
| 待支付态 | 响应可能 `status=pending_payment` + `paymentRecordId` + `payParams`，需 `wx.requestPayment` 调起，回调后才 `active`，不可当失败 | 无 `pending_payment`、无 `payParams`、无 `repay` | 用户付完看不到结果，或把待支付当失败重下 |
| 续付 | `POST /merchant/ads/{id}/repay` | 接口未封装 | 待支付广告无法续付 |
| 类型 | `MerchantAdQuote` / `MerchantAdQuota` 新增 `wechatPaymentEnabled` | 两类型均无此字段（`types.ts:2989/3002`） | — |

### 2.2 阻塞点：本仓没有微信支付调起能力

全仓检索 `requestPayment` / `chooseWXPay` / `WeixinJSBridge` / `jweixin` / `payParams` / `prepayId`：**0 命中**。

本仓是 Vue3 + Capacitor 的 PC/Web 管理端，`wx.requestPayment` 是微信 JSAPI / 小程序能力，这里做不到。因此 v8.26 §2.2 第 3~4 步（调起支付、轮询确认）**无法在本仓实现**。

### 2.3 建议拆法

**本仓可做（本轮）**

1. 支付方式收敛为 `free` / `wechat` 两项，删 `coin` / `point` / `mock`；
2. 默认值改为：有免费额度 → `free`，否则 → `wechat`；都不可用时禁止提交并提示；
3. `MerchantAdQuote` / `MerchantAdQuota` 补 `wechatPaymentEnabled`，微信入口显隐改由它驱动，进件状态降级为辅助文案；
4. 类型补 `pending_payment` 状态 + `paymentRecordId` + `payParams`，列表给「待支付」标签；
5. 封装 `POST /merchant/ads/{id}/repay`。

**本仓做不了（需小程序端）**

- `wx.requestPayment` 调起；
- 支付结果轮询；
- 待支付态的续付闭环。

**需产品/后端定**：管理端展示「待支付」广告时，用户点「继续支付」跳到哪里？小程序页路径是什么？还是管理端只读展示、不允许续付？

> 另请后端确认：`wechatPaymentEnabled=true` 但通道未配置时仍返回 `10002 在线支付未开通`。前端只有一个布尔值，无法区分「功能开放但通道没配好」和「功能被关掉」。是否可在 quote/quota 里补一个更细的状态（如 `wechatPaymentDisabledReason`）？

## 3. 住户钱包：接口全缺，且归属要先定

### 3.1 现状

| 项 | 后端 | 前端 |
|---|---|---|
| `GET /wallet/my` | 已实现（Roles: resident） | **无**（全仓 `/wallet/` 0 命中） |
| `POST /wallet/withdrawals` | 已实现 | **无** |
| `GET /wallet/withdrawals` | 已实现 | **无** |
| `POST /property-coins/transfer-to-wallet` | 保持不变 | **无**（只接了 `/property-coins/earn`、`/use-condition`） |
| 管理端 `withdrawalType=resident_wallet` | 已支持 | `WITHDRAWAL_TYPE` / `WITHDRAWAL_TYPE_LABEL` / `ROLE_WITHDRAWAL_TYPE_OPTIONS` **均缺** `resident_wallet` |

即：后端这一整条链（奖励金 → 转钱包 → 查询 → 提现 → 审核完成冲减）前端只差最后一段——管理端审核筛选里没有这个类型，审核员在「全部角色」下能看到记录，但无法按「住户钱包」筛，也没有中文类型名（会显示 `—`）。

### 3.2 注意与「卖货钱包」的区别

本仓已有 `resident-seller-wallet`（业主卖货钱包，`/resident-merchants/seller-wallet/*`，`WITHDRAWAL_TYPE.RESIDENT_SELLER = 'resident_seller'`）。v8.26 新增的是**奖励金（物业币）转出的钱包**，`withdrawalType = resident_wallet`，两者是不同资金池：

| | 卖货钱包 | 住户钱包（v8.26） |
|---|---|---|
| 资金来源 | 商城卖货差价 | 个人奖励金 `residents.coin_balance` 转入 |
| withdrawalType | `resident_seller` | `resident_wallet` |
| 家庭池 | — | **不参与** |

**不能复用页面，也不能混用类型值**，否则审核端金额对不上。

### 3.3 建议

- **管理端侧（本仓必做）**：`WITHDRAWAL_TYPE` 补 `RESIDENT_WALLET: 'resident_wallet'`、LABEL 补「住户钱包提现」、`ROLE_WITHDRAWAL_TYPE_OPTIONS` 补筛选项。这一项不依赖任何决策，可立即做。
- **住户侧（需定归属）**：本仓 `residentMenus` 目前只有「我的店铺 / 卖货钱包 / 公开橱窗」，可以加「我的钱包」。但 `GET /wallet/my` 的角色是 `resident`，如果住户端 UI 主要在小程序，本仓就不该重复实现。**请确认住户钱包页面落在管理端 Web 还是小程序。**

### 逐条与原文的偏差说明

- **第 10 项**：`/admin/platform-config` 对应页面 `admin/PlatformConfig.vue` 已有 `canEdit` 判断（`:disabled="... || !canEdit"`），无需改动。三组里只差 `settlement-config` 与 `order-config` 两处。
- **第 11 项**：本页编辑弹窗**没有 `role` 表单字段**（新增时固定 `role: 'resident'`，`buildUpdatePayload()` 也不含 role），所以「role 下拉只对 platform_admin 开放」无处落地——目前状态是「无人可改 role」，符合 §102.4 的实质要求。若后续要开放改角色，必须只在 platform_admin 下渲染该下拉。
- **第 5 项回退值取 `true` 而非 `false`**：后端 v8.26 默认值即 `true`。字段缺失时回退 `true`，最坏是提交收到 `10002 在线支付未开通`、用户改用免费额度；回退 `false` 会把微信入口直接藏掉，免费额度用尽的商家将彻底无法投放。
