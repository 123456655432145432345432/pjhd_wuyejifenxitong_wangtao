## 权限配置板块审计（仅核查，未改代码）

结论：**能落库 ≠ 能回显 ≠ 能控制前端可见性**，三层要分开。

1. 数据与写入都是真的：`permissionApi`（users / permissions / role-presets / userPermissions /
   grant / revoke / changeLogs）全部真实落库；`effectivePermissions = 角色预设 + 个人授予 − 个人撤销`。
2. **后端确实按权限项校验**：API 文档第 400 行明确说明 Spring Security `anyRequest().permitAll()` 不做路径 ACL，
   角色/登录态由 `AuthInterceptor` 兜，而 **`/admin/**` 额外经 `PermissionInterceptor` 做权限项校验**。
   文档里显式标注了权限项的只有 `merchant:audit`（§70.5/70.6/70.7 等 4 处），其余接口没给「权限码→接口」映射表。
3. **前端完全不消费权限码**（已全仓验证）：除 `views/Permission.vue` 与 `stores/permission.ts` 外，
   `hasPermission / permissionCode / effectivePermissions` 零引用。菜单= `constants/menus.ts` +
   `PLATFORM_ADMIN_ONLY_ROUTES` + `PROPERTY_LEADER_ONLY_ROUTES` 按 role 硬控；路由= `meta.roles`；
   按钮= 各页内 `isPlatformAdmin` computed。
   → 后果：配了权限但角色没菜单 = 看不到入口；菜单在但权限被撤销 = 能进页面然后 403。两者互不相通。

已确认的具体缺口（可作为后续整改清单）：
- `selectAccount()` 丢弃了接口返回的 `grantedPermissions` / `revokedPermissions`，只看 `effectivePermissions`
  → 页面无法区分「角色预设自带 / 个人额外授予 / 被单独撤销」三态。
- `applyPreset()` 直接覆盖当前勾选（保存才落库），且没有只读的「查看预设内容」入口。
- `grantPermissions()` 未传 `reason` → 变更日志里没有授权原因。
- `PERMISSION_MODULE_LABEL`（enums.ts:1021）未覆盖且非中文的 module 会落到「其他」分组。
- 新做的平台交易明细不带权限码 → 不会出现在权限池里（正好符合「不可被授权开放」的要求）。
