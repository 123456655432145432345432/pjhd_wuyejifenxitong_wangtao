## 权限配置模块审计（只读分析，未改代码）

**背景**：用户测试「给角色/账号加『参数配置』权限 → 用该角色登录 → 看不到参数配置页」，怀疑权限配置功能未真正实现。

**结论**：权限配置只做了「配置端」，没做「消费端」。

- 配置端完整：`views/Permission.vue`（411 行）+ `stores/permission.ts`（274 行）+ `services.ts` L1150–1195，接通文档 §48.1–48.9 七个接口，grant/revoke 真实落库。
- 消费端为零：`AppSidebar.vue` L74 菜单走 `getMenusForProfile(role/propertySubRole/标签)`；`router/index.ts` L950–962 守卫只看 `meta.roles`；无 `hasPermission()`、无 `v-permission`、无 directives 目录。`permissionApi` 全仓仅被 `stores/permission.ts` 引用。
- 页面准入：`permission`、`param` 路由均 `roles=[platform_admin,property_admin] + propertyLeaderOnly`，业务角色（merchant/courier/coordinator/...）进不来，也进不了 `GET /admin/users` 的配置范围。

**发现的契约问题（已写入交付文档）**：
- P0-1 文档内权限码格式矛盾：§48.2/48.6/48.7 用 `resident:read`，§48.3/48.4 预设用 `permission.resident.read`。前端 `applyPreset` 直接 `Set.has()` 比对 → 格式不一致时全部勾不上，此时保存会把原有权限全部 revoke（误清权限风险）。
- P0-2 §48.7/48.8 grant/revoke Roles 仅 `platform_admin`，但前端对 property_admin 领导开放保存 → 必然 403。
- P0-3 权限码只保护 `/admin/**`（文档 §0：SecurityFilterChain 为 permitAll），业务接口多不在该前缀下，门控口径不一致。
- P1-1 `profile`/`admin-login` 未下发 `permissions` 字段（types.ts L23–34、L36+），前端无法得知自己有哪些权限码；且 merchant/courier 调 `/auth/profile` 返回 20004。
- P1-2 缺「权限码 ↔ 前端路由」映射表，是"配置端有、消费端无"的结构性原因。
- P2-1 保存不回写 `rolePresetId`；P2-2 未采集 `reason`。

**产出**：`docs/权限配置_前端现状与后端对接_2026-10-29.md`（给后端）。

**待用户决策**：是否启动消费端改造（需后端先给 #1 编码规范 / #4 映射表 / #5 profile 权限码）；本轮按项目约定未改任何代码。

## 权限配置 v1.3：按后端《管理端权限与工作台》完成对接（21:20 后）

**后端的定性纠正（重要，覆盖此前结论）**
- 活动组长郑美丽的 `residents.role` 是 `resident`，不是 `activity_leader`；身份在 `roleCodes` / `isActivityLeader`。
- 新增 `adminWorkspace` 作为管理端总开关；`effectivePermissions` 是菜单/路由/按钮的唯一依据。
- 本次后端只对标签身份开放 `community:read` / `community:manage`（`grantableToTagIdentities=true`），其他管理权限只给物业管理员。
- 后端只把社区论坛和权限配置改为权限驱动（§8），其余菜单保持角色逻辑，与前端已有的「声明式白名单」方向一致。

**代码落点**
- `constants/permissionCodes.ts`：`community-forum` 映射由 `community:manage` 改为 **`community:read`**（tab 显示条件）；新增 `appendMenusByPermission()`（只删不加的过滤无法让活动组长出现新 tab，必须补追加层）。
